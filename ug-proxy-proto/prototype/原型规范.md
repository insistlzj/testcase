# HTML 原型规范（通用）

> 通用版，适用于任意项目。原型是需求的唯一事实来源：**审核通过的原型 = 开发依据**，需求变更直接改原型，不留历史版本。
>
> 某个具体项目的特有内容（页面清单、公共实体口径、特殊要求、进度）写在该项目自己的专属文档里，不混进本文件。

## 1. 定位

- 高保真：真实配色、间距、组件样式，原型即 UI 稿，开发直接照做。
- 可点击：跨页真实跳转，关键交互（弹窗、Tab、下拉、抽屉）可操作。
- 零构建：纯静态文件，双击 HTML 即可在浏览器打开，不依赖网络与服务器。

## 2. 目录结构

```
prototype/
├── index.html          # 查看器：页面树 + iframe 预览 + 批注面板
├── 原型规范.md          # 本通用规范
├── <项目>-原型说明.md    # 项目专属文档：页面清单/公共实体/进度（可选）
├── assets/
│   ├── tailwind.js     # Tailwind 浏览器版（本地化，离线可用）
│   ├── tokens.js       # 设计令牌：Tailwind 主题配置（色彩/字体/圆角）
│   ├── common.js       # 公共交互：弹窗、Tab、下拉、Toast
│   ├── mock.js         # 共享 Mock 数据
│   └── annotations.js  # 原型批注：每页的业务逻辑/交互/权限说明
└── pages/
    └── *.html          # 每个页面一个文件
```

## 3. 页面规范

- 文件名：英文 kebab-case，按"模块-页面"命名，如 `project-detail.html`、`bug-list.html`。
- `<title>`：`页面名 · 模块名 · 项目名`。
- 每页统一引入：`tailwind.js`、`tokens.js`、`common.js`、`mock.js`。
- 所有页面登记进 `index.html` 的页面树；页面间业务跳转用相对链接。
- **一节点一文件**：页面树的每个节点对应 `pages/` 下的一个 HTML 文件，严禁多个节点指向同一文件。弹窗、抽屉、Tab、空态等同页画面不另立树节点，用「页面状态」（§7）收进它所属的文件。判据：**会不会生成一个独立 HTML 文件？** 会 → 立节点；不会 → 写进所属文件，可在节点标题括注「含 A/B/C」提示该页内含哪些画面。
  > 反例（务必避免）：把"导出弹窗""空态"各列成树节点、都指向同一个文件 → 点哪个都是同一默认画面，既冗余又误导（同事点"导出弹窗"却看不到弹窗）。
- **统一骨架**（复制一个已完成页面改最快）：

  ```
  <head>    charset / viewport / title / tailwind.js + tokens.js / common.js / mock.js / 少量 <style>
  <body>
    1. 页面主体   —— 与真实 UI 一致的成品态
    2. 弹层       —— 弹窗 / 抽屉 / 遮罩
    <script>
      1. 页面渲染（从 Mock 渲染）
      2. 交互逻辑（弹窗开合 / 表单 / 下拉等）
      3. registerStates 页面状态注册（见 §7）
  ```

## 4. 视觉规范（设计令牌）

- 所有颜色、字号、圆角、阴影只从 `tokens.js` 的主题配置取，页面内不出现魔法色值。
- 基础令牌：主色 `primary`、成功 `success`、警告 `warning`、危险 `danger`、中性灰阶；圆角统一 `rounded-lg`；正文 14px。
- 通用组件写法在首个页面中确立后即为标准（按钮、表格、标签、表单、弹窗），后续页面复用同样的 class 组合，不另起炉灶。

## 5. 交互规范

> **可点必有反馈，不留"死控件"。** 原型会被拿去照着开发；一个点了没反应的按钮，要么被当成 bug，要么被当成"该功能不存在"，两种都误导。

- **干净优先**：页面单独双击打开就是干净的成品态。状态切换、批注等评审层控件一律由查看器渲染，不写死在页面可视区——混在页面里的原型专用控件会被误读成功能。
- 凡可交互的元素（按钮 / 行 / 标签 / 下拉 / 输入框），按三类落地：
  1. **同页交互**（弹窗、Tab、下拉、抽屉、选中、表单态）→ 用 `common.js` 提供的极简 JS 真实实现，可真实开合。
  2. **跨页跳转** → 真实 `<a href>` 相对链接。
  3. **打后端**（提交、导出、删除等真实后果）→ 点击弹 Toast 即时反馈，并在批注用业务语言写清"会发生什么、数据怎么变"。
- **有意不实现的也要交代**：属动态/重型、原型不便实现的（无限滚动、拖拽、右键菜单…），转成批注说明而非默默省略——写明"此处真实产品有该交互，原型以批注代替"。
- **输入框完整态**：空内容禁用提交、Enter 提交 / Shift+Enter 换行等边界按真实产品接上，别只放一个静态框。
- 禁止：真实网络请求、路由框架、状态持久化（审核工具条除外）。

## 6. Mock 数据规范

- 全部集中在 `mock.js`，页面从中渲染或直接静态写入，但**实体必须全局一致**：同一批客户名、人名、单号贯穿所有页面，让评审像在看真系统。公共实体清单写在项目专属文档里，各页照抄。
- 数据要**仿真但虚构**：形态像真系统——真实感的客户名、日期、金额，禁止 `测试1`、`aaa` 类占位；但内容必须凭空虚构，**严禁取自真实数据、数据库或截图**——既防隐私泄露，也防"假数据被当真数据"。
- **Mock 是字段口径的唯一来源**：字段命名贴近真实接口，后端按它对齐字段含义——Mock 不只是页面填充物，也是数据字典。
- 覆盖边界形态：空态、锁定、超长内容等通过「页面状态」注册演示（见 §7）；每类数据至少放一条极端数据（超长文本、空值等）用于演示边界。

## 7. 查看器（index.html）与原型批注

查看器是浏览原型的统一入口，布局四区：

- **顶部操作栏**：打开/关闭页面树、打开/关闭批注面板、当前页面名、**页面状态切换**、缩放比例。
- **页面状态**：一个页面的不同形态（未输入、空态、锁定、错误等）不拆成多个文件，而是在页面脚本里注册，查看器顶栏出现状态控件，点击切换演示。状态可有**多个相互独立的维度**（如 列表态 × 主题 × 权限），按维度分组注册、查看器为每组渲染一个下拉，而不是把各维组合平铺成一排按钮：`registerStates({ '列表': { '正常': fn, '空态': fn }, '主题': { '浅色': fn, '深色': fn } })`；单维页面可用简写 `registerStates({ '状态名': 应用函数 })`。每组默认第一个状态。
- **左侧页面树**（可折叠）：按模块分组、组可展开收起，点击在中间预览。
- **右侧批注面板**（可折叠）：展示当前页面的**原型批注**——业务逻辑、交互规则、权限、边界情况等页面本身画不出来的信息。开发与测试通过"原型 + 批注"理解整个项目，批注即需求说明。
- **中间预览区**：iframe 加载页面，iframe 逻辑尺寸 = 浏览器窗口尺寸（宽高比一致），按预览区可用空间等比缩放，所见即全屏效果。

批注集中维护在 `annotations.js`，按页面文件名组织、按主题分节；跨页面的全局规则（导航栏、个人面板、登录态等）挂在 `'*'` 键下，在所有页面的批注面板顶部显示。批注与页面一起产出、一起更新，不允许页面改了批注没改；只写页面上看不出来的有效规则，写与不写没有区别的批注不写。

## 8. 工作流

1. 按需求文档拆页面清单 → 生成原型 + 批注；
2. 负责人在查看器里逐页浏览，修改意见直接在开发会话中反馈，改后复查；
3. 确认后原型冻结，进入开发；开发、测试以"原型 + 批注"为需求依据；需求变更先改原型再改代码。

> 各项目的**页面清单**（页面 / 文件 / 要点三列表格）维护在该项目的专属文档里，作为拆页与验收的依据，不写入本规范。
