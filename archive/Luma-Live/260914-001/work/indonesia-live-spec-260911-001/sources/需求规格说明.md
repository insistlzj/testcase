# 印尼直播需求规格说明（聊天提炼版）

> 来源：[李浩_佘柱湘_问答整理.md](李浩_佘柱湘_问答整理.md)
>
> 本文只收录聊天中已得到直接、可执行且无明显冲突的规则。其证据状态为“聊天明确”，不等同于正式需求已审批，也未验证当前代码、原型或线上行为。冲突、缺失和待决内容见 [需求待确认.md](需求待确认.md)。

## 直播间与开播

| 编号 | 需求 | 来源 |
| --- | --- | --- |
| REQ-LIVE-001 | 受限直播间应统一展示直播封面图、毛玻璃遮罩和对应操作弹窗；弹窗类型包括购买门票、输入密码和被拉黑提示。 | Q006 |
| REQ-LIVE-002 | 直播间礼物应支持特效；个人装扮道具不使用礼物特效。 | Q013 |
| REQ-LIVE-003 | 礼物特效文件应在详情页展示，列表页不展示。 | Q014 |
| REQ-LIVE-004 | 直播访问量按进入次数统计，不按账号去重；同一账号进入 5 次计为 5 次。 | Q015 |
| REQ-LIVE-005 | 不提供“断流但场次不结束”的独立功能，原型中的该功能应删除。 | Q016 |
| REQ-LIVE-006 | 后台强制关闭门票直播间时，不自动退还观众已支付的门票。 | Q017 |
| REQ-LIVE-007 | 主播退出旧公会、成为普通用户并再次加入新公会后，后台保留其全部历史记录；主播端只展示加入新公会后产生的数据；旧、新公会分别只能查看主播在本公会期间的数据。 | Q018 |
| REQ-LIVE-008 | 主播 ID 与直播间 ID 为同一标识；主播身份发生退出和恢复时，固定直播间不得变化。 | Q019 |
| REQ-LIVE-009 | 任务入口应跳转到独立页面并展示全部任务。 | Q020 |
| REQ-LIVE-010 | 用户退出密码房后，如果主播修改了本场密码，用户再次进入时必须输入新密码。 | Q037 |
| REQ-LIVE-011 | 主播将 App 切到后台时，观众端展示最后一帧；超过 120 秒后直播间自动结束，暂停期间计入直播时长；主播 App 被杀时直播间立即结束。 | Q039 |
| REQ-LIVE-012 | 首页轮播应支持多张素材滚动展示；同一条轮播规则可以配置多条轮播内容。 | Q041 |
| REQ-LIVE-013 | 用户端推送对象支持“全部”和“指定公会”：选择全部时推送给所有用户，选择公会时只推送给该公会成员。 | Q046 |
| REQ-LIVE-014 | 礼物适用范围选择器应展示全部礼物，包括未上架礼物。 | Q074 |
| REQ-LIVE-015 | 直播过程中不得转换直播间房型。 | Q105 |
| REQ-LIVE-016 | 开播设置必须包含门票价格选择。 | Q113 |
| REQ-LIVE-017 | 美颜使用“选项 + 滑块”交互；可用美颜项数量由购买套餐决定。 | Q128 |
| REQ-LIVE-018 | 主播相关的 3 个入口对所有用户展示；非主播点击“开始直播”或“主播中心”时，跳转到主播身份引导页面。 | Q130 |
| REQ-LIVE-019 | 首页“热门”和“新人”列表不等同于用户关注列表。 | Q131 |
| REQ-LIVE-020 | 直播消息卡片应展示房间封面图、直播间主题、主播名称及房型信息；普通房、密码房、门票房均展示封面图。 | Q122 |
| REQ-LIVE-021 | 主播列表中的状态字段表示主播“开播权限”是否正常。 | Q123 |
| REQ-LIVE-022 | 密码房同时开启“在广场中展示”和“从粉丝中授权可见”时，仅授权名单内用户可在首页看到直播间，并可在输入正确密码后进入。 | Q072、Q083 |
| REQ-LIVE-023 | 密码房授权名单存在历史选择时，再次设置应自动选中上次选择的用户。 | Q094 |
| REQ-LIVE-024 | 主播答谢观众采用固定口头答谢内容；点击答谢后进入对应答谢页面。 | Q087 |
| REQ-LIVE-025 | 直播间应区分两类贡献榜：在线观众贡献榜，以及本场累计贡献榜；后者包含在线和已离线观众。 | Q088 |
| REQ-LIVE-026 | 主播页面的“粉丝”数量按关注该主播的用户数统计，不按粉丝团人数统计。 | Q070 |

## 粉丝团、聊天与房管

| 编号 | 需求 | 来源 |
| --- | --- | --- |
| REQ-SOC-001 | 每个主播默认拥有 1 个粉丝团，目前最多只能拥有 1 个；单个粉丝团成员上限为 500 人。 | Q052、Q143 |
| REQ-SOC-002 | 用户达到主播设置的粉丝团条件后不会自动入团，仍需主动加入；人数达到 500 时，加入按钮置灰并显示“成员已满”，只有主播移除成员后才可继续加入。 | Q055 |
| REQ-SOC-003 | 粉丝团与粉丝群聊是同一业务实体；加入群聊即加入粉丝团，群聊已满时不能加入粉丝团。 | Q059 |
| REQ-SOC-004 | 用户加入粉丝团后，不得查看加入前的群聊历史消息。 | Q064 |
| REQ-SOC-005 | 被主播踢出直播间的用户在本场直播结束前不得重新进入，包括再次付费进入。 | Q053 |
| REQ-SOC-006 | 陌生人私信发送上限按方向独立计数：A 到 B 最多 3 条，B 到 A 也可独立发送最多 3 条。 | Q057 |
| REQ-SOC-007 | 删除好友或会话关系时，双方聊天记录均清空，并从双方对话列表中删除。 | Q062 |
| REQ-SOC-008 | 直播间只使用账号级拉黑；被主播拉黑的用户再次进入直播间时应显示拉黑提示。 | Q060 |
| REQ-SOC-009 | 主播不得处置其他房管，原型中的该能力应删除。 | Q049 |
| REQ-SOC-010 | 巡房账号可以接收主播发起的拉黑或踢出操作，但巡房身份和巡房能力不受这些操作影响。 | Q051 |
| REQ-SOC-011 | 解除单人禁言后用户立即恢复发言；用户进入主播下一场直播时也应恢复发言。 | Q066 |
| REQ-SOC-012 | 单人禁言与全员禁言应分别独立生效和解除；任一禁言状态存在时，用户都保持禁言。 | Q115 |
| REQ-SOC-013 | 用户与主播任一方建立账号拉黑关系时，应自动取消该用户的房管权限。 | Q110 |
| REQ-SOC-014 | 群成员不得编辑群资料，仅群主可以编辑。 | Q125 |
| REQ-SOC-015 | 客服入口不接独立客服系统，优先跳转客户的 WhatsApp 会话。 | Q133 |

## 金币、礼物与订单

| 编号 | 需求 | 来源 |
| --- | --- | --- |
| REQ-FIN-001 | 金币以整数形式存储，不支持小数金币。 | Q024 |
| REQ-FIN-002 | 幸运礼物概率配置保留 1 位小数。 | Q027 |
| REQ-FIN-003 | 幸运礼物 RTP 计算结果除不尽时，向上取整并保留 1 位小数。 | Q028 |
| REQ-FIN-004 | 道具上架不代表所有用户自动拥有；道具获取途径包括完成任务、金币购买和达到等级。本期只实现道具配置，不实现具体获取逻辑。 | Q030 |
| REQ-FIN-005 | 主播收益计算：门票、普通礼物和定制礼物按礼物价值计入；幸运礼物按礼物价值的 1% 计入，且与返奖无关。 | Q036 |
| REQ-FIN-006 | 榜单贡献计算：门票、普通礼物、定制礼物和幸运礼物均按礼物价值计入。 | Q036 |
| REQ-FIN-007 | 系统金额统一使用 USD，金额展示也使用 USD。 | Q068、Q069 |
| REQ-FIN-008 | 支付成功后发生全额退款时，不恢复该订单已占用的活动套餐限购次数。 | Q073 |
| REQ-FIN-009 | 订单退款或冲正不影响主播收益计算。 | Q075 |
| REQ-FIN-010 | 充值金币订单支持后台退款；购买礼物订单不支持后台退款。 | Q080 |
| REQ-FIN-011 | 系统不提供提现功能。 | Q089 |
| REQ-FIN-012 | 财务统计仅保留收益、累计充值和累计退款三个指标。 | Q091 |
| REQ-FIN-013 | 充值套餐的赠送比例由“套餐本金”和“套餐赠送金币”计算；示例中的比例必须与实际赠送数量一致。 | Q101 |
| REQ-FIN-014 | 用户只有 1 个资金账户，不拆分本金账户和赠金账户；除充值外获得的金币归类为赠金，仅供报表统计。 | Q135 |
| REQ-FIN-015 | 所有消费统一从余额扣减，不逐笔追踪消费使用了哪次充值获得的金币。 | Q135 |
| REQ-FIN-016 | 充值订单退款时，从当前余额扣除该充值套餐的本金金币与赠送金币总额。 | Q135 |
| REQ-FIN-017 | 后台按套餐配置赠送金币的绝对数量，不直接配置百分比；用户入口显示 `+xxx 金币`，并计算各套餐中的最高赠送比例用于提示。 | Q137、Q139 |
| REQ-FIN-018 | 运营账号不持有真实金币，只持有公会发放的虚拟金币；运营账号不能充值、做任务或发送幸运礼物。 | Q111 |
| REQ-FIN-019 | 直播间密码只能由数字组成。 | Q071 |

## 任务、奖励与等级

| REQ-TASK-002 | 同一任务中的奖励档位值不得重复。 | Q078 |
| REQ-TASK-003 | 邀请奖励为固定规则；任务奖励允许后台配置。 | Q081 |
| REQ-TASK-004 | 用户已达到较高档位后，如果后台新增较低档位，用户应立即具备领取该新增档位奖励的资格。 | Q084 |
| REQ-TASK-005 | 用户同时达到多个奖励档位时，界面优先展示最早尚未领取的档位奖励。 | Q117 |
| REQ-TASK-006 | 每日任务在当日达成但未领取的奖励，于次日清空并作废；奖励必须由用户主动领取。 | Q117、Q118 |
| REQ-TASK-007 | 连续登录奖励配置到第 `z` 天时，第 `z+1` 天及以后继续按第 `z` 天的最高档奖励发放。 | Q140 |
| REQ-TASK-008 | 系统至少包含主播等级和财富等级两类等级。 | Q144 |
| REQ-TASK-009 | 财富等级与用户累计打赏金额相关。 | Q142 |

## 公会与运营后台

| 编号 | 需求 | 来源 |
| --- | --- | --- |
| REQ-GUILD-001 | 公会被停用时，应自动从公会推荐中移除；重新启用公会时不得自动恢复原推荐。 | Q079 |
| REQ-GUILD-002 | 公会中只存在主播成员，不保留“普通成员”类型。 | Q082 |

| REQ-GUILD-005 | 后台用户数据范围来自用户 App 中的全部用户。 | Q050 |
| REQ-GUILD-006 | 运营位只保留“直播广场运营位”和“福利中心轮播位”；不提供首页轮播位和个人中心运营位。 | Q099 |
| REQ-GUILD-007 | 同一运营位类型内的素材排序由该类型自己的权重决定，不跨类型混排。 | Q104 |
| REQ-GUILD-008 | 已发送的推送不得取消。 | Q138 |

## 验收口径

- 每条需求都必须能追溯到上表所列 Q 编号及其原消息。
- 本文中的“应/不得”表示从聊天回答提炼出的可测试行为，不表示已经验证实现。
- 开发和测试开始前，应先处理 `需求待确认.md` 中与本条需求相关的冲突；待确认结论优先于本文旧口径，并应同步更新来源记录。
