# 用户 APP 原型分析报告

日期：2026-08-08

## 一、结论

1. `prototype/index.html` 已登记 31 个用户/主播端 HTML，文件均存在；页面树实际只显示 29 个节点，没有文件路径失效。
2. `粉丝贡献排行榜`、`工会申请记录` 已画但未挂入页面树。
3. 用户侧“浏览普通房—聊天—送礼—退出”可演示；登录、搜索、榜单、密码房、个人成长、设置与安全未闭环。
4. 主播侧“开播设置—主播直播间—结束直播—查看数据”可演示；主播认证、完整开播设置、PK、粉丝团设置、场次详情、提现申请与详情未闭环。
5. 当前原型可用于局部页面评审，不足以作为完整开发依据。查看器状态切换已报错，且 31 个用户端页面中只有 4 个配置了批注。

## 二、页面树问题

### 2.1 已画但页面树不可见

| 页面 | 文件 | 现有业务入口 | 问题 |
| --- | --- | --- | --- |
| 粉丝贡献排行榜 | `fan-contribution-ranking.html` | 我的粉丝团 → 本月粉丝榜 | HTML 和入口已存在，页面树未显示 |

原因是 `index.html` 中“我的粉丝团”“工会中心”子容器没有被加入页面树。

### 2.2 目录和编号不清晰

- `直播数据`、余额、余额明细、订单详情、用户主页被放在用户 APP 一级，与实际归属不一致。
- `我的 · P011` 与 `群管理（群主）· P011` 编号重复；`P004/P005/P013` 缺失。
- 原型说明登记 29 个用户端页面，但漏了两个直播结束页；页面树则漏了粉丝贡献排行榜和工会申请记录，两份清单不是同一组 29 页。

建议归属：

- `直播数据 / 直播记录 / 收益提现 / 粉丝团` 归入主播中心。
- `余额 / 余额明细 / 订单详情` 归入我的 → 钱包。
- `用户主页` 归入消息、好友、直播间用户卡等来源页面。

## 五、用户视角流程评估

| 流程 | 当前状态 | 判断 |
| --- | --- | --- |
| 首次启动 → 注册/登录 → 首页 | 缺失 | 用户主流程没有起点 |
| 首页发现 → 搜索/榜单/筛选 → 进房 | 部分可用 | 普通房、门票房可演示；搜索、榜单、密码房不完整 |
| 观看 → 评论/关注/送礼 → 退出 | 基本可用 | 主要动作有反馈；清晰度、横竖屏、断流重试、余额不足充值未覆盖 |
| 主播资料 → 加好友/私信/粉丝团 | 部分可用 | 用户主页和私信可走；主播公开主页、好友申请处理不完整 |
| 消息 → 会话/群聊/通知 | 部分可用 | 文本私信、群聊可用；图片/语音、系统通知、好友申请、普通会话跳转不足 |
| 任务/邀请 → 领奖 → 资产变化 | 部分可用 | 签到和领奖有反馈；邀请中心、任务全集、奖励流水未闭环 |
| 我的 → 钱包/关系/装扮/设置/安全 | 不完整 | 钱包基础页可用；资料、关系、装扮、设置、客服、申诉缺失 |

用户侧结论：核心观看演示较顺，但“登录—发现—互动—沉淀关系—复访”链路在入口和留存环节断开。

## 六、主播视角流程评估

| 流程 | 当前状态 | 判断 |
| --- | --- | --- |
| 加入工会 → 认证 → 开通直播权限 | 缺失 | 主播身份获取过程无法评审 |
| 主播入口 → 开播设置 → 开播 | 部分可用 | 标题、封面、分类、房型可操作；标签、美颜、滤镜、清晰度和权限异常缺失 |
| 主播直播间 → 用户识别/管理 → 结束 | 基本可用 | 观众、贡献榜、用户卡、禁言、踢出、拉黑、房管、结束直播已覆盖 |
| PK/连麦 | 缺失 | 只有 Toast，没有邀请、接受、分屏和结束状态 |
| 粉丝团经营 | 部分可用 | 成员排序和移除可用；创建、设置、单人/全员禁言未覆盖 |
| 直播结束 → 数据/记录 → 场次复盘 | 部分可用 | 汇总和趋势清晰；场次与日明细无法继续查看 |
| 收益 → 提现 → 审核/打款结果 | 未闭环 | 展示了入口和记录，但申请、详情、驳回原因、金额冻结变化未画 |

主播侧结论：直播中的经营和秩序管理最完整；直播前的资格、直播中的 PK/设置、直播后的提现与复盘均有断点。

## 七、影响评审的共性问题

1. 页面状态切换不可用：`common.js` 发送 `groups`，`index.html` 读取 `states`，查看器报错，热门/新人、普通用户/主播、房管等状态无法从顶栏切换。
2. 批注不足：用户端 31 页只有首页、福利、消息、我的 4 页有批注。权限、异常、数据变化和跨页规则没有成为原型事实。
3. 一级导航口径冲突：页面架构写“首页 / 消息 / 任务 / 我的”，原型是“首页 / 福利 / 消息 / 我的”。需先统一“任务”与“福利”的定位和顺序。
4. 提现口径冲突：角色与用例已写明线上提交提现工单，项目需求清单仍写一期线下结算。应先同步文档，再补提现原型。
5. 状态覆盖不足：登录异常、空列表、网络/直播错误、余额不足、权限关闭、审核驳回、支付失败等关键边界缺失。

## 八、下一轮建议顺序

1. 先修查看器状态协议、页面树、编号、页面说明和批注框架。
2. 第一批补用户 P0：启动登录、搜索、榜单、密码房、主播主页、好友申请。
3. 第二批补个人与身份：资料编辑、设置、邀请中心、主播认证、工会状态。
4. 第三批补主播闭环：完整开播设置、PK/连麦、粉丝团设置、场次详情、提现申请与详情。
5. 每批完成后同步 `index.html`、页面文件、`mock.js`、`annotations.js` 和原型说明，并按用户/主播主流程重新走查。
