# D:\testcase_html 测试用例生成规则

## 0. 快速执行区

本节用于快速定位，不替代后文细则。执行时按“范围 -> 接入 -> 证据 -> 同步 -> MainBasis 更新与版本核对（已配置项目） -> 输入隔离 -> 独立规则库 -> 业务对象状态转换基线 -> 目标端场景投影 -> 已有用例映射 -> 缺口生成 -> 覆盖验证 -> 最终校验 -> Excel”顺序处理；同一要求只在对应稳定规则编号下定义，其他章节只引用编号。

### 0.1 规则用语

- `必须`、`不得`、`禁止`：强制要求，不满足时停止当前阶段。
- `允许`、`可以`：满足所列条件时可采用，不得扩大解释。
- `建议`：不影响门禁，可根据当前证据和风险选择。
- 规则冲突时，先执行当前任务中用户明确确认的最新要求；未发生需求变化时，按本文件的证据优先级和稳定规则编号执行。

### 0.2 核心规则索引

| 稳定规则编号 | 负责内容 | 不通过时 |
| --- | --- | --- |
| `SCOPE-01` | 适用范围、文件职责、视觉测试边界 | 停止扩大范围 |
| `GATE-01` | 候选、单条用例与批次的质量校验和阻断边界 | 局部隔离或批次阻断 |
| `EVID-01` | 来源策略、证据优先级、冲突处理 | 进入需求待确认或停止同步 |
| `CASE-01` | 正式用例的证据、数据、动作和结果门槛 | 不生成正式用例 |
| `ROLE-01` | 目标端入口、执行角色、查看视角和观察位置 | 拆分角色或进入需求待确认 |
| `SCAN-01` | 全局证据扫描、缓存、依赖和基线 | 按影响范围隔离或批次阻断 |
| `GAP-01` | 规则缺失复核 | 不得声称缺失 |
| `ONBOARD-01` | 新项目首次接入和项目隔离 | 停止正式生成 |
| `INPUT-01` | 输入角色、规则清单、历史隔离和哈希 | 局部隔离或批次阻断 |
| `BASIS-01` | 上游同步、MainBasis 两文档更新和用例输入版本衔接 | 返回需求同步；不得使用过期基线 |
| `DISC-01` | 从原始证据独立发现规则、场景和真实覆盖缺口 | 未解释内容局部复核；虚假覆盖声明不得通过 |
| `STATE-01` | 业务对象生命周期、状态转换、三端投影和流程闭环 | 缺失转换局部待确认；虚假闭环不得通过 |
| `SYNC-01` | 原型与派生需求同步 | 进入需求待确认或批次阻断 |
| `RESULT-01` | 业务结果完整性和过程态覆盖 | 补充覆盖或待确认 |
| `SCHEMA-01` | JSON、Excel和需求待确认字段 | 隔离问题项或停止受影响产物 |
| `LANG-01` | 描述、子项、步骤、预期和语言词表 | 隔离问题用例 |
| `DEDUP-01` | 规则归一化、单结果拆分和语义去重 | 隔离相关用例或批次阻断 |
| `EXCEL-01` | 工作簿命名、格式、公式和可编辑区域 | 停止交付 |
| `DELIVERY-01` | 交付前总检查 | 按 `GATE-01` 处理 |
| `CHANGE-01` | 规则修改、日志和回退 | 规则修改未完成 |

### 0.3 固定执行顺序

1. 按 `SCOPE-01` 确认范围、目标端、角色、交付格式和视觉测试要求。
2. 按 `ONBOARD-01` 确认项目身份，再按 `EVID-01` 读取来源策略。
3. 按 `SCAN-01` 选择扫描模式并建立证据闭环；`prototype-primary` 项目同时执行 `SYNC-01`。配置 MainBasis 的项目先执行 `BASIS-01` 的版本检查，有变化时完成需求更新，再进入用例阶段。
4. 按 `GAP-01` 完成缺失复核，再按 `INPUT-01` 建立输入清单和当前规则清单。
5. 按 `STATE-01` 以共同业务对象建立来源状态、动作、目标状态和观察端的状态转换基线；跨端流程先完成状态连续性检查。
6. 按 `RESULT-01`、`ROLE-01` 和测试设计章节，将状态转换及非状态规则投影为各目标端场景；不满足 `CASE-01` 的内容按 `GATE-01` 进入候选层或用例层隔离。
7. 按 `DISC-01` 固定独立场景库后才读取已有用例，先映射真实覆盖，再按 `LANG-01` 和 `DEDUP-01` 生成缺口用例。
8. 输入、规则、状态转换、候选、历史比较和证据哈希通过后，将符合门槛的用例与已隔离的“需求待确认”生成最终 JSON 与 Excel；不得要求所有覆盖点都转成正式用例。
9. 按 `DELIVERY-01` 完成交付检查；规则文件有修改时同时执行 `CHANGE-01`。

### 0.4 [GATE-01] 用例生成质量校验与阻断机制

质量校验用于保证正式用例可靠，同时保留不受局部缺口影响的有效覆盖。发现问题后必须先确定最小影响范围，再区分可继续处理、需要隔离和必须阻断；禁止使用“一处问题导致整个流程停止”的粗粒度策略。

#### 0.4.1 候选层：允许生成

需求解析不完整、角色映射存在疑问、原型或批注有歧义、部分业务规则不能完全确认，或者只能形成合理推断而缺少明确依据时，允许保留候选测试点，但必须：

- 写入“需求待确认”，明确已知依据、缺失信息、影响范围和确认后待补用例；不得混入“测试用例”数组。
- 不把推断写成确定业务规则，不给出无依据的确定性预期。
- 不影响其他证据明确、可以执行和观察的正式用例继续生成。
- 在规则清单和覆盖清单中保留处理去向，不得通过删除疑问项使门禁通过。

例如，原型只说明“关闭功能后影响展示效果”，但没有说明是否影响历史数据或其他端展示时，可以在“需求待确认”中保留“关闭功能后其他端展示状态是否变化”的候选场景，并将影响范围标记为待确认；不得生成“其他端展示必然变化”的正式用例。

#### 0.4.2 用例层：局部隔离

单条用例缺少明确角色、具体操作入口、可验证结果、可准备测试数据，或者描述存在歧义时，只隔离该用例及其直接依赖：

- 记录问题原因和关联规则，标记 `可生成正式用例=false`，必要时转入“需求待确认”。
- 不进入正式用例集；其他符合要求的用例、模块和任务阶段继续处理。
- 修正时只重建受影响规则、用例及其下游哈希和产物；禁止因单条用例问题重新生成全部用例。

正式用例的质量标准不降低。任何进入正式用例集的记录仍必须满足 `CASE-01`、`ROLE-01`、`LANG-01` 和 `DEDUP-01`。

#### 0.4.3 批次层：整体阻断

只有以下系统性风险允许停止当前批次：

1. **输入完整性问题**：无法确认测试对象、项目范围或需求来源，输入内容与目标任务不匹配，项目身份或输入角色混乱，或者关键证据和哈希基线无法建立。
2. **核心规则冲突**：同一核心需求存在互相矛盾的业务规则，无法依据适用版本、生效时间或替代关系判断有效规则，且冲突会导致本批次主要测试结果完全不同或无法限定到局部规则。能够限定到单个功能、角色、场景或结果的冲突必须局部隔离，不得整批阻断。
3. **交付结果无法保证**：要求的输出格式无法生成，数据结构无法形成，文件损坏，候选与最终结果无法保持一致，或者关键内容缺失到无法形成可用交付物。

批次阻断时必须停止生成错误结果，输出阻断原因、影响范围和需要补充的信息。扫描未完成、文件无法读取或依赖未展开时，只有无法限定影响边界或破坏公共证据闭环才构成批次阻断；可以定位到具体规则或模块时按候选层或用例层处理。

#### 0.4.4 信息不足与影响分析

信息不足时不得编造业务规则，不得把推断作为确定需求；可以基于经验提出候选测试场景，但影响预期结果的信息必须标记为“需求待确认”，并继续处理不受影响的内容。

对于开启、关闭、删除、修改、切换和状态变化，必须主动分析当前模块、上下游模块、不同角色、数据状态和后续流程的影响。该分析只用于发现覆盖点和证据缺口；只有存在明确业务依据时才能生成确定性预期，无依据的影响关系统一标记为“待确认影响范围”。

#### 0.4.5 正式交付与最终优先级

正式交付前，每条正式用例必须做到测试目标明确、操作步骤可执行、预期结果可验证、无明显重复，并且不把未确认规则写成确定结果。交付物允许包含已隔离问题、需求待确认和候选测试场景；这些内容必须与正式用例清楚分离且可追溯。

不得因局部问题阻断整体交付，不得删除所有存在疑问的内容，也不得使用大量模糊描述代替实际验证。执行优先级固定为：业务理解正确 -> 保留有效覆盖 -> 隔离局部不确定因素 -> 仅在系统性风险出现时阻断。

## 1. [SCOPE-01] 适用范围与文件职责

本文件适用于 `D:\testcase_html` 下测试用例的生成、审查、修正和 Excel 交付。

- `AGENTS.md`：唯一的规则来源，集中定义强制质量门禁、证据边界、标准工作流、测试设计规则、统一字段、Excel 交付标准和回退机制。业务规则治理内容只在本文件维护。
- `Cem Kaner.txt`：JSON 用例生成的执行模板，只定义任务输入、执行入口、对本文件章节的引用、JSON 输出契约和合法示例；不得再次完整复制本文件的证据、同步、扫描、测试设计、去重或质量门禁正文。
- `规则文件变更日志.md`：根目录唯一的规则变更日志，集中记录 `AGENTS.md` 和 `Cem Kaner.txt` 的每次修改及回退依据。
- `新项目首次接入指令.md`：定义根目录新增项目的身份盘点、项目说明和来源策略草稿、用户确认、正式登记及首次全量扫描门禁。
- `全局证据扫描指令.md`：定义首次全量、后续增量、缓存失效、回退全量和证据基线复核规则。
- `原型与需求清单同步指令.md`：定义生成用例前核对原型并同步 `context/` 需求清单的执行步骤和保护措施。
- `需求清单变更日志.md`：根目录唯一的需求清单同步日志，集中记录各项目 `context/` 需求清单的自动修改、依据、影响和回退内容。
- `<项目>/需求来源策略.json`：声明该项目采用的来源策略、原型目录、允许自动修改的派生需求清单、公共证据清单和同步开关。派生需求清单是写入白名单，不是证据读取白名单。
- `<本次任务work目录>/generation-input-manifest.json`：声明当前项目目录、本次全部输入文件的路径、哈希、角色和允许用途，是当前业务证据、本次派生产物、历史参照、样式参照与执行工具之间的强制隔离清单。
- `<本次任务work目录>/state-transition-baseline.json`：由当前规则清单归一化得到的业务对象生命周期基线，记录来源状态、触发动作、执行角色、操作端、目标状态、观察端、分支和证据；不得脱离当前规则清单新增业务事实。
- `scripts/validate-generation-input.mjs`：分阶段校验输入角色、文件哈希、当前规则清单、历史比较结果、生成脚本引用和候选/最终 JSON 一致性；校验失败时按 `GATE-01` 隔离受影响规则，只有输入完整性、核心规则或结果一致性失效时阻断批次。
- `scripts/validate-testcase-json.mjs`：直接读取本文件 `LANG-01` 机器规则区，校验 JSON 字段、单结果、字段重复、含糊表达、通用占位词和预期结果序号；可定位到单条用例的问题先隔离该用例，数据结构或文件整体不可用时停止 Excel 交付。
- `Cem Kaner.txt` 与本文件冲突时，以本文件为准。修改本文件中的治理规则时，只有任务输入或 JSON 输出接口发生变化才同步修改 `Cem Kaner.txt`；不得为了保持两份重复正文一致而双重维护同一规则。
- 默认生成业务功能测试，不生成颜色、字体、间距、像素、纯排版、图片美观度等视觉用例；用户明确要求 UI 视觉测试时才补充。

## 2. 证据与推断边界

### 2.1 [EVID-01] 证据优先级

已完成首次接入的项目，生成前必须先读取项目根目录的 `需求来源策略.json`。新项目缺少该文件时先按第 2.4 节执行首次接入，不得直接使用默认策略生成用例。允许以下三种来源策略：

- `prototype-primary`：审核通过的原型和批注是当前页面、入口与交互来源，`context/` 需求清单是派生文档；项目存在已登记的系统概要时，系统概要是派生需求同步中的最高业务规则来源。生成用例前必须先按第 3.1 节同步需求清单。
- `requirement-primary`：正式需求和验收标准优先，原型只用于补充页面结构和交互证据；原型冲突进入“需求待确认”。
- `conflict-review`：任何无法依据版本、生效时间或替代关系解决的来源冲突均进入“需求待确认”，不自动覆盖任一来源。

在任一来源策略下，必须以资深 QA 视角执行证据分析。提取业务规则前，必须按照当前项目的来源策略，结合页面结构、可执行交互、动态状态、批注上下文及其他当前证据，建立“执行角色 -> 页面入口 -> 触发动作 -> 必要条件或状态 -> 可观察结果”映射；不得将页面元素清单、静态展示值或 Mock 示例直接当作业务规则。完成业务规则归一化后，再按 `RESULT-01`、`ROLE-01` 和测试设计章节建立测试覆盖并生成测试用例；证据不足或冲突的内容按 `EVID-01`、`GAP-01` 进入“需求待确认”。

已登记的旧项目未声明策略时默认使用 `conflict-review`，不得自行假定原型或需求优先；新项目只能在首次接入草稿中建议 `conflict-review`，经用户确认后才能成为正式策略。当前任务中用户明确确认的来源策略高于项目配置，但必须在需求清单变更日志中记录本次覆盖原因。

在 `requirement-primary`、`conflict-review` 或没有项目策略时，按以下顺序确定业务规则：

1. 用户在当前任务中明确确认的规则。
2. 正式需求、验收标准、概要设计和接口契约。
3. 原型便签、标注、交互说明、提示文案和状态描述。
4. 当前代码、数据库约束和自动化测试中可以形成完整调用链的明确行为。

已有测试用例、历史 Excel、历史任务 JSON、历史扫描缓存和测试启发式不是业务规则来源。它们只能用于发现检索词、识别覆盖候选、比较变化、追溯编号或补充风险维度；其中的前置条件、步骤、预期结果、备注和待确认结论不得直接复制为当前候选用例。代码当前实现不能单独证明业务预期。多个来源相互冲突时，不得仅按文件日期新旧自行选择；只有来源明确说明适用版本、生效时间、废止范围或替代关系，并且可以确认适用于当前任务时，才能采用当前有效规则，同时在备注中写明判断依据。无法确认适用关系时，必须写入“需求待确认”。

`prototype-primary` 项目的派生需求清单按以下规则同步：

1. **取并集补充**：系统概要、审核通过的原型页面或结构化批注明确存在，而派生需求清单缺失的当前功能或规则，必须补充到可唯一定位的需求文件和章节。系统概要可以证明跨端业务规则，但不能单独证明某个目标端存在页面、按钮或查看入口；目标端入口仍须满足第 2.2.1 节。
2. **系统概要优先**：系统概要与原型、批注或派生需求清单描述同一业务规则且内容冲突时，以系统概要为准修改派生需求清单，并在同步结果中保留冲突来源和采用理由。系统概要没有覆盖该事项时，采用原型或批注明确表达的页面、字段、可执行交互、动态状态和操作结果。
3. **删除孤立条目**：某项派生需求仅存在于需求清单，并且经过第 2.3.1 节规则缺失复核后，确认系统概要、全部关联原型页面和结构化批注均不存在该功能或规则时，从派生需求清单删除。未完成全量关联检索、来源文件缺失或无法读取时属于扫描阻塞，不得执行删除。
4. **保留直接证据**：删除前必须在 `需求清单变更日志.md` 保存被删除的完整原文、已检索范围、未命中结论和回退方法。系统概要或原型仅未描述某个细节、但仍明确存在对应功能时，不得删除整个功能；只清理无来源的具体阈值、状态、流程或结果。

上述规则只适用于项目配置明确列入 `派生需求清单` 的文件，不用于自动删除正式需求、验收标准、系统概要、原型、批注或其他公共证据。代码、Mock 示例和历史用例不能单独阻止孤立条目清理，也不能替代系统概要、原型或批注创建派生业务规则。

原型内部出现以下特定差异时，作为来源冲突规则的明确例外处理：页面初始化的默认展示值、占位值或 Mock 记录中的示例数据，与同一页面批注明确写明的默认规则、筛选规则、状态含义或计算口径不一致时，以批注为准。页面默认值和 Mock 示例不得据此建立与批注相反的业务规则，也不单独写入“需求待确认”或阻断同步；证据索引和用例备注必须记录批注位置以及被批注覆盖的展示或示例差异。批注未明确给出规则、无法判断页面值是否属于默认或示例数据，或者差异涉及真实可执行交互、字段结构、枚举、数据类型、状态切换或操作结果时，仍按来源冲突处理。

### 2.2 [CASE-01] 可执行用例门槛

正式测试用例必须同时具备：

- 可识别的功能、规则、角色或状态来源。
- 可准备的前置条件和测试数据。
- 可执行的操作。
- 有依据且可观察的预期结果。

允许根据证据使用等价类、边界值、状态转换、错误猜测等方法扩展测试输入，但不得据此编造提示文案、阈值、权限、状态去向、计算公式或跨系统影响。

缺少确定性预期时，不生成正式用例；按 `GATE-01` 将该测试点写入“需求待确认”，不影响其他正式用例。

解析不完整、角色映射未完成或测试数据尚未设计时，规则状态使用“生成待复核”且 `可生成正式用例=false`，按候选层保留已知依据、缺失信息和处理去向。复核必须回到当前证据；完成 `GAP-01` 后仍缺少业务决定的，转为“需求待确认”。能够定位到具体规则或用例时不得阻断其他内容；只有无法识别测试对象、范围、来源或影响边界时才按 `GATE-01` 阻断批次。

### 2.2.1 [ROLE-01] 目标端可执行性与规则归属门禁

全局证据扫描发现业务规则后，必须继续核对该规则在本次目标端的承载方式，不能把“系统存在规则”直接等同于“目标端存在查看或操作入口”。生成正式用例前，应建立“规则来源 -> 适用角色和端 -> 实际入口或触发动作 -> 可观察结果”的映射。

1. **逐步核对目标端入口**：正式用例中的每个页面、按钮、详情、说明、明细、弹窗、列表和跳转动作，都必须有目标端原型元素及交互、目标端批注、明确指定目标端的正式需求，或可形成完整调用链的当前实现作为依据。仅有系统概要、后台配置页、其他端页面或已有用例，不能证明本次目标端存在该入口。
2. **区分规则可见性和业务结果**：目标端没有规则查看入口，不代表规则无效或没有测试价值。若目标端可以执行相关业务并观察余额、状态、消息、记录或其他确定结果，只生成这些可执行、可观察的结果用例，不得补写不存在的“查看规则”“打开详情”或“查看明细”步骤。
3. **按实际观察位置归属**：规则只能通过管理后台、接口、数据库、日志或测试工具验证时，应归入相应端、接口或数据层测试范围；这些来源在当前模块中保留为关联证据，但不得伪装成当前端操作。用户未要求扩大范围时，记录覆盖去向，不自动生成其他端用例。
4. **保留有价值的证据缺口**：业务规则有明确依据，但当前目标端缺少入口、操作路径或观察方式时，不得简单删除该覆盖点。应根据缺口性质写入“需求待确认”或覆盖清单，询问是否需要目标端入口、入口位置、展示内容或可观测方式；不同决定按父子问题规则拆分。
5. **处理原型与派生需求差异**：`prototype-primary` 项目中，派生需求写明目标端应展示某规则，但系统概要未指定该端入口，且审核通过的原型没有对应入口、批注或可执行交互时，按第 2.1 节完成规则缺失复核后清理该展示入口。若系统概要明确业务规则但未定义目标端入口，保留业务规则及关联证据，不得据此生成目标端展示类正式用例；入口是否需要补充进入“需求待确认”。
6. **按角色与查看视角拆分**：同一端、同一功能名称被多个角色或身份使用时，必须先建立“执行角色/账号身份 -> 查看视角 -> 实际页面或入口 -> 可见字段和可执行动作 -> 可观察结果”映射。入口、字段、权限、操作或结果任一不同，必须拆成不同稳定规则和不同用例；不得在一条规则的“适用角色和端”中合并后，再用“用户”“查看列表”“打开详情”等未指明执行者的表述生成用例。正式用例只能包含一个执行角色和一个查看视角；角色在 `功能模块`、`功能结构` 中仍不能唯一识别时，`功能结构` 使用“功能名称（角色视角）”，并在前置条件或操作步骤中写明执行角色。只有当前证据明确多个角色使用相同入口、动作和结果时才允许合并，且仍需选择一个可执行角色作为本条路径；某一角色缺少入口或结果证据时不得由其他角色视角推定。

### 2.3 [SCAN-01] 全局证据扫描门禁

生成任一模块测试用例前，必须执行根目录 `全局证据扫描指令.md`。采用“首次全量、后续增量、失效自动回退全量”的组合方案；全局扫描用于建立业务关联和证据边界，不自动扩大用户指定的测试范围。

项目 `需求来源策略.json` 中的 `派生需求清单` 只限定 `prototype-primary` 同步时允许自动修改的文件，不得据此缩小证据读取范围。`公共证据清单` 用于显式登记系统概要、业务对象、角色权限、页面架构等跨模块文件；即使项目没有登记该字段，扫描时发现的全部 `context/` 文件、项目说明引用文件和其他关联来源仍必须纳入候选证据清单。

1. **每次重建轻量清单**：对项目候选证据文件记录相对路径、文件大小、修改时间和 SHA-256，计算项目指纹。轻量清单用于判断变化，不等于每次重新语义读取全部文件。
2. **分层缓存与扫描模式**：缓存按 `文件清单 -> 证据原子 -> 归一化规则、状态转换和依赖 -> 候选用例与历史比较 -> 工作簿` 分层保存，每层记录输入哈希、Schema 版本、产物哈希和下游依赖。没有有效证据层时使用 `full`；缓存有效且变化可沿依赖关系定位时使用 `incremental`；增量过程中发现未知依赖、映射断裂或失效条件时切换为 `fallback-full`。上游层失效时只废弃该层及下游层，仍满足输入哈希和 Schema 的上游层可以复用。
3. **按影响范围失效**：项目标识、正式证据入口、来源策略或证据原子提取 Schema 变化，候选证据新增、修改、删除总数达到 30 个或达到前后文件数较大值的 20%，以及用户明确说明整体替换项目时，证据层执行 `full`。业务规则、生成、同步或质量门禁变化时，必须在规则基线中声明最早受影响层；只要证据原子结构和来源哈希仍兼容，可以从该层向下重建，不得仅因规则文件哈希变化重复语义读取全部未变化证据。无法判断最早受影响层时，从证据原子层重建。
4. **清理失效层**：扫描模式确定后，在语义读取开始前清理或隔离本次已判定失效的缓存层，并在 `global-evidence-scan-result.json` 记录层名、旧文件相对路径、SHA-256、清理时间和结果。`full`、`fallback-full` 必须清理证据原子及全部下游层；规则或输出层局部失效只清理对应层及下游层。清理失败、仍残留被判定失效的缓存文件或缺少记录时阻断扫描；历史任务快照、历史用例、测试输出及仍有效的上游缓存不得删除。
5. **细粒度依赖扩展**：依赖索引至少建立 `文件 -> 页面或章节 -> 共同业务对象 -> 端 -> 模块 -> 角色或身份 -> 来源状态 -> 动作 -> 目标状态 -> 状态转换标识 -> 稳定规则标识 -> 用例编号` 映射。增量模式只重新语义读取变化文件和依赖闭包；目标模块直接来源、未变化公共来源和已复用证据仍需核对当前 SHA-256。需求、批注、Mock、共享配置或接口指向其他端或模块时继续展开，直至共同业务对象、上游触发、当前行为和下游结果闭合。历史用例只能提出待复核线索。
6. **限制测试范围**：管理后台、公会端、第三方等来源只作为当前测试范围的关联证据；除非用户明确要求，不生成这些端自身的模块用例。未影响当前范围的文件记录为已建档但不纳入，并写明原因。
7. **保存缓存与任务快照**：项目级缓存保存在 `work/<项目目录名>-global-evidence-cache/`，`latest.json` 保存各层清单和当前指针，各层产物保存在 `layers/`；每次任务在自己的 `work/` 目录保存 `global-evidence-scan-result.json`。两者必须记录扫描模式、模式依据、规则基线及影响层、项目指纹、文件变化、各层读取和复用证据、排除原因、依赖关系、关联映射、规则缺失复核、缺口及阻塞项。新的或更新后的项目级缓存只能在全部交付门禁通过后发布。
8. **双重基线校验**：任务开始时固定所有读取或复用证据的 SHA-256；生成最终 JSON 和 Excel 前重新计算。任一证据变化时本次结果失效，重新选择扫描模式后再生成。
9. **处理不完整扫描**：缺少有效项目指纹、失效层未完成清理、缓存证据与当前哈希不一致，或者公共证据、依赖和关联映射不完整到无法限定影响边界时，按 `GATE-01` 阻断批次。缺失来源或依赖能够定位到具体规则、角色或模块，并且其余证据闭环仍完整时，只隔离受影响内容并记录排除依据，不得阻断其他内容。来源完整扫描后仍缺少业务决定的事项进入“需求待确认”，不能用待确认掩盖实际扫描失败。
10. **记录阶段耗时**：每次任务保存 `pipeline-metrics.json`，至少记录清单与哈希、语义读取、同步、规则归一化、候选生成与去重、历史比较、JSON 校验、Excel 生成、Excel 检查各阶段的开始时间、结束时间、耗时、输入数量、输出数量和复用数量，并标出耗时最长阶段。缺少阶段记录不得声称流程已完成优化；同范围、同扫描模式下明显变慢时记录原因和后续处理，不因追求速度跳过质量门禁。

### 2.3.1 [GAP-01] 规则缺失判定复核门禁

在声称“规则未定义”“需求不存在”“证据缺失”，或据此生成“需求待确认”前，必须完成以下复核；只看到某一份需求清单未写、只读到章节标题或只检查目标端页面，均不能作为缺失结论：

1. **拆分检索对象**：提取业务对象、角色、动作、来源状态、目标状态、限制条件和可观察结果，并补充原文简称、同义词、旧称、页面名称和数据字段名。不得只搜索生成者最先想到的一个词。
2. **覆盖全部关联来源**：检索并语义读取目标端需求、系统概要、业务对象、角色与权限、页面架构、原型页面及脚本、公共批注、公共 Mock、其他端需求、接口契约和代码链路。来源策略未列为派生需求的现存文件也必须检查。历史用例可以补充检索词和覆盖候选，但命中内容必须回到当前来源复核，历史文本本身不计为规则命中。
3. **阅读命中上下文**：关键词命中后必须阅读所属章节、表格整行、相邻条件和直接引用，不能只看标题、搜索摘要或单行片段。一个来源明确规则、另一个来源未提及，不属于冲突或缺失。
4. **建立复核记录**：每个拟判定缺失的规则记录“检索对象、检索词、已查文件、命中位置、命中内容、采用结论和未采用原因”，写入全局扫描结果的 `规则缺失复核`。同一业务规则的多来源命中合并记录。
5. **优先转换明确规则**：任一合格来源已经给出适用范围和确定结果时，应纳入证据索引并生成对应正式用例；不得继续把该规则列为缺失或需求待确认。目标端没有查看入口时仍按第 2.2.1 节只生成可执行、可观察的结果用例。
6. **区分未命中与扫描失败**：全部已登记和扫描发现的关联来源均完成复核但仍无确定结果，才可判定为证据缺口；应存在的文件缺失、项目说明引用失效、文件无法读取或关联链路未展开时属于扫描阻塞，不得伪装成业务规则缺失。
7. **复核新增缺口**：生成覆盖清单和需求待确认后，按业务对象再次反查新增缺口；发现遗漏命中时撤销错误缺口，补入正式规则和受影响用例。

### 2.4 [ONBOARD-01] 新项目首次接入门禁

用户在 `testcase` 根目录新增项目后，必须先执行根目录 `新项目首次接入指令.md`，不能因为新项目缺少 Luma Live 的同名文件就直接判定资料缺失，也不能读取其他项目的资料补齐当前项目。

1. **识别新项目**：用户明确说明为新项目，或者项目没有状态为 `已确认` 且稳定项目标识匹配的接入记录，也没有可核对的旧项目兼容依据时，视为新项目候选。仅删除普通扫描缓存不会使已有有效接入记录的项目重新变成新项目；分支或提交变化本身不改变稳定项目标识。
2. **只读盘点**：先读取当前项目实际存在的 README、项目说明、需求、验收标准、原型、批注、Mock、代码和已有测试资料，记录项目路径、Git 远程地址、分支和提交；不得套用其他项目的目录模板或业务规则。
3. **仅生成草稿**：缺少 `项目说明.md` 或 `需求来源策略.json` 时，只能在本次 `work/` 目录生成 `项目说明草稿.md`、`需求来源策略草稿.json` 和 `project-onboarding-result.json`。未知内容标记“待用户确认”，默认只能建议 `conflict-review`。
4. **禁止未确认写入**：用户确认前不得在新项目目录创建或修改项目说明、来源策略、`context/` 或原型文件，也不得生成正式测试用例 JSON 或 Excel。
5. **确认后登记**：用户明确确认项目身份、证据入口和来源策略后，才按确认内容落地正式文件，并保存 `work/<项目目录名>-project-onboarding/latest.json`；首次正式生成必须执行 `full` 全量扫描。
6. **兼容已有项目**：规则生效前已经存在 `项目说明.md`、`需求来源策略.json`，历史全局证据缓存的扫描状态为 `通过` 或 `有非阻塞待确认`，并且缓存中的项目目录及这两个核心文件 SHA-256 与当前项目一致时，可以直接视为已接入。核心文件已合理修改但尚未扫描时，需要用户明确确认这是原有项目而非新增或替换项目。兼容项目在下次通过首次全量扫描后补建接入记录；历史缓存即使因本次规则或 Schema 变化失效，也只能作为身份依据，不得复用其中的业务证据。
7. **项目隔离**：每个项目独立维护接入记录、来源策略、扫描缓存、任务目录和输出目录；不得跨项目复用业务证据、缺口结论或测试用例。

### 2.5 [INPUT-01] 生成输入隔离门禁

每次生成、增量修订或重审测试用例时，必须在本次任务 `work/` 目录先建立 `generation-input-manifest.json`。当前规则清单完成后、候选用例生成前执行 `scripts/validate-generation-input.mjs --phase pre-generate`；历史比较和最终 JSON 完成后执行 `--phase final`。清单是各阶段生成输入的完整白名单；未登记文件不得被相应脚本读取后用于业务规则、步骤或预期结果。

1. **固定项目与输入角色**：清单必须记录本次唯一的 `项目目录`；除本次任务内允许的用户确认记录和已确认决策摘录外，`当前业务证据` 必须位于该项目目录，不得读取相邻项目作为当前规则来源。每个输入只能标记为 `当前业务证据`、`风险与缺口`、`本次派生产物`、`历史参照`、`样式参照` 或 `执行工具`。`风险与缺口` 禁止定义正式业务规则。清单至少记录 `路径、SHA-256、角色、内容类型、允许定义业务规则`；同一路径不得登记多个角色。MainBasis 项目的阶段与角色边界另按 `BASIS-01` 执行。
2. **限制规则来源**：只有 `当前业务证据` 可以作为最终业务事实来源。`本次派生产物` 中仅 `business-rule-catalog.json` 可以承载由当前证据归一化后的规则；其每条规则必须反向引用清单中哈希一致的当前业务证据。`state-transition-baseline.json` 只能组合规则清单中已有的业务对象、状态、动作、角色、端和结果，不得独立定义业务事实；每项转换必须反向引用规则标识和当前证据。扫描结果、同步结果和质量报告本身不能替代原始证据。
3. **隔离历史输入**：旧 JSON、旧 Excel、旧任务目录、历史扫描结果和历史缓存统一标记为 `历史参照`，`允许定义业务规则` 固定为 `false`。独立规则库和场景库固定前不得读取已有用例内容；固定后可按 `DISC-01` 映射、复核并保留当前证据仍支持的既有用例。既有用例不能反向定义规则、场景或覆盖分母；历史待确认结论不能直接视为当前需求缺失。
4. **限制 work 目录资格**：`work/` 下的文件默认不是当前业务证据。仅本次任务保存的当前用户明确确认记录，或从正式决策载体中提取并完成当前适用性复核的 `confirmed-decision-extract.json`，可以标记为 `当前业务证据`；其余文件只能是本次派生产物、历史参照、样式参照或执行工具。决策摘录必须记录原文件路径和哈希、精确位置、已确认结论、适用范围、当前适用性和判断依据；原文件仍作为历史参照，测试用例区域不得随摘录进入当前证据。其他项目和其他任务目录中的文件不得标记为当前业务证据。
5. **先建当前规则清单**：生成候选用例前保存 `business-rule-catalog.json`。每条规则至少记录 `稳定规则标识、业务对象、共同业务对象、执行角色、适用角色和端、触发动作、必要条件、来源状态、目标状态或可观察结果、规则状态、可生成正式用例、证据引用`。`共同业务对象` 用于合并三端对同一申请、订单、账号、直播场次或关系的不同页面称呼；没有跨端关系时与业务对象相同。正式规则只能包含一个执行角色、一个动作和一个可观察结果；同一条件影响多个角色或动作时拆成多个规则。候选层或用例层隔离项必须设置 `可生成正式用例=false`；尚未确认的执行角色、动作或结果允许为空或记录待选范围，但必须在覆盖清单和“需求待确认”中说明缺失信息和处理去向。稳定规则标识必须由归一化业务键生成或沿用，不得依赖数组顺序。`证据引用` 必须包含当前证据路径、SHA-256、位置和证明内容；来源冲突、证据缺口或生成待复核的规则不得标记为可生成正式用例。
6. **后做历史比较**：当前候选完成后，才读取历史参照并保存 `historical-case-comparison.json`。先提取历史备注中已有的稳定规则标识并精确匹配；没有标识或标识失效时，只在相同模块、角色和动作类别的业务键桶内做语义回退比较。报告必须记录候选 JSON 的路径和 SHA-256、匹配方式及实际比较次数；历史用例只能绑定当前稳定规则标识，并判定为 `继续有效`、`需要重写`、`合并`、`已被替代`、`应当废弃` 或 `待人工复核`。历史文本与当前规则不一致时以当前证据为准，不能把历史内容回写到规则清单或直接修改候选。
7. **生成顺序固定**：执行 `DISC-01` 和 `STATE-01` 的源证据发现顺序。第 6 项的“候选完成后”在新流程中指状态转换基线、独立场景及其覆盖契约已固定，不能继续理解为先生成全部用例再证明完整。已有用例映射发现新线索时，回到当前证据重新建立规则、状态转换和场景基线，禁止直接从历史文本增加业务规则。
8. **保持候选内容不被历史改写**：历史比较全部关闭后，最终 JSON 的文件 SHA-256 必须与报告记录的候选 JSON 一致。若需修改任何正式字段，原候选失效，必须先更新当前规则清单并重新生成候选、历史比较和哈希；不得在历史比较后对候选执行局部补丁。
9. **记录用例规则映射**：质量上下文必须记录每条正式用例对应的稳定规则标识；没有当前规则映射、只引用历史编号，或者只引用 `work/` 历史文件的用例不得交付。最终输入清单必须追加候选 JSON、历史比较结果和最终 JSON 及其哈希。输入清单、规则清单或历史比较存在未关闭的 `待人工复核` 时，先定位并隔离受影响规则或用例；只有输入完整性失效、无法定位影响范围或候选与最终结果无法保持一致时，才阻断批次。

### 2.6 [DISC-01] 规则和场景独立发现

已配置 MainBasis 的项目按 `BASIS-01` 划分上下游阶段：本节所指当前源证据在用例阶段只指已发布的两份 MainBasis 文档；全局原型和关联证据的发现、补漏及缺失复核在需求更新阶段完成。

1. **独立输入与三级模型**：发现阶段只接收当前原型、批注、需求、页面及递归关联证据，不接收已有用例或预先编写的场景清单。先保存原始证据单元及定位，再提取业务规则；对存在生命周期的共同业务对象，按 `STATE-01` 建立状态转换；最后将转换和非状态规则投影为目标端场景。业务规则允许包含多个条件和结果分支；第 2.5 节第 5 项的单动作、单结果约束施加于状态转换投影、场景和正式用例，不得据此退回“一规则一用例”。
2. **独立状态与场景库**：保存 `business-rule-catalog.json`、`state-transition-baseline.json`、`test-scenario-library.json` 和发现基线。规则、转换和场景标识来自语义条件，不依赖已有用例数或 `add(...)` 调用。只有会改变状态或可观察结果的有效条件才展开，不做全维度笛卡尔积。不支持解析的条款或缺失状态记录为“生成待复核”或“待补转换”，不得算作已完成建模的场景，也不得伪装成需求待确认。
3. **先映射再补缺口**：固定场景及覆盖契约后，按规则、页面、角色、操作、状态、分支映射已有用例，逐项记录已覆盖、未覆盖、待确认或不适用。来源仍有效不等于场景已覆盖；只有必要条件、实际动作和明确断言均满足场景契约才能声明已覆盖。随后只对未覆盖且具备执行依据的场景生成用例；保留既有用例的源证据复核和新旧编号对应。
4. **维度与元素覆盖**：15 维判断以结构化条件、边界、状态和结果为依据，不能通过用例文本关键词命中数量计算覆盖率。不适用须引用明确依据；没有建立适用性或未完成建模时记录未覆盖/生成待复核。每个页面元素单独绑定其状态、操作、结果与场景；页面名称已映射、按钮数或字段数一致均不足以声明元素已覆盖。
5. **证据门禁**：重新读取当前源文件，核对哈希及原文，重演完整条款提取和场景发现，再核对每个已覆盖声明的条件、动作、断言、角色和页面来源。只有编号、关键词、格式或关系完整不能通过。必须用来源变更和伪造覆盖的回归样例证明门禁会拒绝错误条件、错误结果和无依据不适用。设计覆盖与产品执行结果分开；未执行的用例保持“未测”。
6. **局部隔离与真实统计**：原始条款数、已结构化规则数、场景数、已覆盖数、未覆盖数、待建模条款及历史待复核问题分别报告。只放行可用部分时必须披露其余缺口，不能把“声明真实性校验通过”写成“全部语义覆盖完成”。未关闭的局部缺口不得删除，也不阻断其他明确分支。
7. **当前执行入口**：已配置 MainBasis 的项目使用 `BASIS-01` 和同步指令第 3.9 节进入本次新任务，由生成执行者只从两份文档建立规则、共享状态和场景，复用结构化设计渲染及共用质量校验；不得调用仍直接读取原型的旧发现入口。未配置 MainBasis 的单端直播模块继续使用 `scripts/build-live-discovery.mjs discover` 和 `generate <既有用例JSON> <既有规则清单>`。两端及以上范围先建立共享状态转换基线，再按端投影。`work/` 下旧生成和直接导出脚本仅供历史追溯，不是新任务入口；旧任务中“直接生成/跳过复核”的授权不得跨任务继承为默认规则。Schema 3.2 继续由共用校验器转入 `scripts/validate-discovery.mjs`，但不得以 Schema 版本绕过 MainBasis 输入边界；手工复核的结构化设计可使用现有 Schema 1.0 接口，仍须独立保存并验证状态和场景基线。

### 2.6.1 [BASIS-01] MainBasis 更新与生成衔接

本节适用于来源策略中配置 `MainBasis` 的项目。用户只说“生成用例”时自动执行，无需重复要求同步；这是由生成执行者衔接的流程，不是后台定时任务或纯脚本语义转换。

1. **先核对新鲜度**：按同步指令第 3.9 节执行版本检查。上游全项目文件（包括新增、删除、未跟踪文件）、流程规则和两份文档均核对内容哈希；不按文件日期判断。缺少同步基线视为首次衔接，禁止直接认证旧 MainBasis 为最新。上游或文档改变时自动回到扫描和同步，未变化且有效的证据按 `SCAN-01` 复用。
2. **需求更新阶段**：保留项目 `prototype-primary` 策略；系统概要优先，审核通过的原型及明确批注补充系统概要未覆盖事项。执行 `SCAN-01`、`GAP-01`、`SYNC-01` 对比全部 context 文件，但只修改配置白名单中的派生清单。然后汇总更新项目 MainBasis 下配置的两份文档。这两份是单独的输出白名单，不能再当作上游来源参与自我证明；其他 context 文件的差异只记录，不擅自修改系统概要或正式证据。
3. **保留业务与缺口**：统一需求文档包含有来源的规则、角色、入口、状态、端侧观察结果及稳定编号；未确认条目必须明确标记并关联风险问题。风险清单只说明缺口、冲突、影响和待决策事项，不能提供确定预期。保留既有编号和用户已确认结论；按适用性复核更新，不能覆盖或清空产品决策。来源缺失不能通过删除整个功能掩盖。
4. **两文档一起发布**：完成真实语义对比和日志后，保存同步前后哈希、来源映射、隔离问题及复核说明，再发布 MainBasis 基线。脚本只验证版本与记录一致性，不代替业务判断。中途中断或只更新一份文档不得放行。需求基线发布不表示测试覆盖、Excel 检查或项目证据缓存已通过。
5. **用例输入隔离**：生成阶段只有统一需求文档登记为 `当前业务证据/允许定义业务规则=true`；风险清单登记为 `风险与缺口/允许定义业务规则=false`，仅支持隔离规则与待确认问题。两文档内的来源链接仅用于追溯，不在用例阶段沿链接读取原型补写步骤或预期。需要补证据时返回需求更新阶段，更新文档和版本后重建受影响设计。当前用户新确认的业务结论也先落入这两份文档，再进入正式用例。本条是 `INPUT-01`、`ROLE-01`、`GAP-01` 的阶段限定，不降低可执行性和缺失复核要求。
6. **绑定同一版本**：三端共享同一个 MainBasis 基线，分别建立端侧输入清单，记录 `MainBasis基线.路径` 和 `SHA-256`。规则和状态转换从当前文档独立建立后才读取历史用例；不得沿用旧任务的规则/场景分母。候选前、最终 JSON、Excel 导出及缓存发布通过共用校验重验版本；任一变化按影响范围回到同步，不只重新导出旧 JSON。
7. **不修改历史交付**：旧用例、工作簿、历史任务和旧基线保留追溯。新一轮输出使用新编号。历史脚本里写死的旧路径不得替换为当前文档后冒充重新设计；没有完成本节时，不得声称已按最新需求生成。
8. **全新生成模式**：项目配置 `用例生成模式=全新生成`、`历史比较=false` 时，禁止读取旧用例、旧规则库、旧场景库、旧扫描语义结果和归档业务内容，也不读取旧用例寻找检索词。生成顺序为当前上游 -> 重新建立或核对当前 MainBasis -> 独立规则 -> 共享状态 -> 三端场景 -> 全新用例 -> 覆盖验证 -> JSON/Excel；本节覆盖快速流程及 INPUT-01、DISC-01、SYNC-01、DEDUP-01、DELIVERY-01 中的历史映射和比较要求。输入清单固定 `历史策略=不读取不比较`，不得登记历史参照或历史比较结果，不创建空比较报告冒充已比较。阶段耗时将 history-compare 记为“不适用：用户禁用”，旧例影响记为“不评估历史用例”；仍须保证候选与最终 JSON 一致并通过全部非历史质量门禁。该模式不发布用例历史缓存。通用工具允许复用，工具内不得包含旧用例业务设计或默认旧任务路径。原始资料和接入记录保留；历史目录仅可按用户指令恢复，不得自动回读。

### 2.7 [STATE-01] 业务对象状态转换与三端投影

1. **先对象、后端**：两端及以上共同参与同一业务时，生成单位必须是共同业务对象的生命周期，用户 App、公会 App、管理后台只是状态转换的执行端或观察端。不得先分别生成三套场景，再按名称或已有用例编号拼接。
2. **转换最小结构**：每项已确认转换在场景生成前至少记录 `状态转换标识、流程编号、共同业务对象、来源状态、触发动作、执行角色、操作端、目标状态、观察端、分支类型、规则标识、证据`；场景投影完成后再追加目标端和场景标识，不得反向改变已固定的状态语义。同一动作产生多个独立观察结果时按观察端拆成场景，但仍绑定同一状态转换和流程编号。
3. **状态必须有依据**：来源状态、目标状态、角色、动作、端和失败结果必须来自当前规则及其当前证据。只明确动作和结果、但缺少来源状态或下游状态时保留为 `待补转换`；业务决定缺失时进入“需求待确认”。不得用页面标题、按钮文案、常见审批经验或历史用例补造状态。
4. **连续性与分支**：正常、驳回、拒绝、取消、超时和恢复分支分别连接有依据的来源状态和目标状态。后一步来源状态必须能由前一步目标状态到达；无法连接的缺口按具体转换局部隔离。只有无法识别共同业务对象或主要流程状态关系时才按 `GATE-01` 阻断批次。
5. **按端投影**：每个目标端场景只包含该端实际执行角色、入口、动作或观察结果，并绑定 `状态转换标识、流程编号、流程阶段`。其他端动作只能作为已完成的前置状态，不得写进本端操作步骤；其他端结果必须投影为对应观察端场景。
6. **闭环判定**：跨端流程只有同时满足初始状态和终态明确、转换图连续、每项转换有规则和证据、每个操作端及观察端均有场景去向时，才能标记 `已闭环`。结构完整不等于已有用例覆盖；状态转换覆盖、目标端场景覆盖和实际执行结果必须分别统计。
7. **稳定标识与变更**：流程编号由共同业务对象形成的稳定业务键生成或沿用；状态转换标识由共同业务对象、来源状态、动作、执行角色、操作端和目标状态形成。状态、动作或端变化时只重建受影响转换、目标端场景及下游产物，不重新读取未变化证据。

### 3.1 [SYNC-01] 原型与需求清单同步门禁

仅 `prototype-primary` 项目执行自动同步；其他策略只比较和记录冲突，不自动修改 `context/`。同步必须遵守根目录 `原型与需求清单同步指令.md`，并满足以下保护措施：

1. **固定同步来源基线**：同步开始时记录系统概要及本次范围内原型、批注文件的相对路径、修改时间和 SHA-256；本次比较、修改和用例生成只能使用同一基线。同步期间任一相关来源内容发生变化时，本次同步失效，必须重新读取。
2. **按范围增量扫描**：首次同步、策略变化或索引失效时执行全量扫描；平时扫描目标模块及其页面、公共批注、公共 Mock、共享组件和已知跨模块依赖。发现跨端或跨模块关联时自动扩大扫描范围，不得只读单个截图或单页静态文本。
3. **建立稳定映射**：先建立“系统概要规则 / 原型文件 / 页面节点 / 结构化批注 -> 端 -> 模块 -> 功能结构 -> context 文件 / 章节”映射。无法唯一定位需求落点时不得自动修改，记录为“无法定位”的阻塞同步异常。
4. **分类差异**：每项差异只能归入 `新增`、`修改`、`明确删除`、`原型未覆盖`、`来源冲突` 或 `无法定位`。系统概要、原型和批注中的内容缺失于派生需求时归入 `新增`；同一规则与派生需求不同且能够按系统概要优先级解决时归入 `修改`；完成全来源缺失复核后的需求清单孤立条目归入 `明确删除`。原型默认展示值或 Mock 示例数据与明确批注不一致时，按第 2.1 节的原型内部优先级采用批注，不归入“来源冲突”。
5. **限制自动修改范围**：只向派生需求清单同步系统概要明确业务规则，以及原型明确表达的页面结构、入口、按钮、字段、选项、展示文案、真实可执行交互、动态状态、跳转和批注规则；Mock 只补充字段名称、枚举和页面间共享对象口径。只修改与差异直接相关的最小文本，不顺带重排或格式化无关内容。
6. **按角色拆分需求表述**：修改或补充派生需求清单前，必须将每个功能点拆成“适用角色或身份 -> 可执行动作 -> 必要状态 -> 可观察结果”，逐项核对动作归属。不同角色受到同一状态限制，但可执行动作不同时，应分角色列出或拆成独立条目；不得使用“用户”“参与者”等泛称，把某一角色无权执行的动作与其可执行动作并列。例如，证据表明直播关闭后观众不能继续观看、评论或送礼，且观众本身没有连麦权限时，不得再写“观众不能进入连麦”；连麦限制应单独写在具备发起或参与连麦权限的角色下。只有证据明确多个角色的动作和结果完全相同时才允许合并。角色、权限或动作归属证据不足时，记录“来源冲突”或“需求待确认”，不得写入确定性需求。
7. **限制删除条件**：允许删除两类内容：一是系统概要、原型说明、批注、页面状态或用户确认明确写出“删除”“取消”“下线”“废弃”或“不支持”且能定位的条目；二是按第 2.1、2.3.1 节确认只存在于派生需求清单、在系统概要及全部关联原型和批注中均无依据的孤立条目。删除前必须在需求清单变更日志保存完整原文、检索范围和回退方法。只检查单页、静态截图或单一关键词时不得删除。
8. **系统概要优先与隐藏规则**：系统概要明确的权限、金额、公式、统计口径、异步时效、异常恢复、跨端结果、历史数据和兼容规则必须同步并优先于原型或批注冲突内容。系统概要未覆盖但原型或批注明确存在的规则按其证据同步；三者均无依据的需求清单条目按第 7 项清理。来源文件不完整、规则适用范围不明或原型内部存在无法解决的实质冲突时，不执行删除或确定性修改；能定位到具体规则时记录“来源冲突”或“无法定位”并局部隔离，无法限定影响边界时才阻断同步批次。
9. **记录精确变更**：每次实际修改 `context/` 时，在根目录唯一 `需求清单变更日志.md` 追加连续编号，记录项目、原型基线、目标文件和章节、差异分类、原型证据、修改前原文、修改后原文、影响范围、受影响用例和回退方法。没有实际修改时记录同步摘要，不制造空变更条目。
10. **追踪已有用例影响**：比较已有用例与变更后的需求，将相关用例标记为 `继续有效`、`需要重审`、`已被替代` 或 `应当废弃`；不得自动覆盖或删除历史 Excel。需要重审、替代或废弃的用例必须出现在同步结果中。
11. **处理不完整同步**：系统概要或原型公共基线变化、日志写入失败、无法安全回退，或者核心来源冲突无法限定影响范围时，同步状态为 `阻塞`，不得继续当前批次。单条规则缺少直接证据、无法定位或存在局部来源冲突时，隔离受影响规则并进入“需求待确认”，同步状态使用 `有非阻塞待确认`，其他规则继续处理。
12. **输出同步结果**：每次生成任务在对应 `work/` 目录保存同步结果，至少包含策略、同步状态、系统概要与原型基线、扫描范围、目标需求文件、差异统计、日志编号、受影响用例和阻塞异常；最终交付说明应简述新增、修改、明确删除、待确认和受影响用例数量。

### 3.2 [RESULT-01] 业务结果完整性扫描

对提交、保存、新增、编辑、删除、审核、支付、配置、开关、状态切换、批量处理和跨端动作等有业务结果的操作，按实际风险检查以下观察维度，不机械凑数：

对于开启、关闭、删除、修改、切换和状态变化，还必须主动分析当前模块、上下游模块、不同角色、数据状态和后续流程。分析结果只有获得明确业务依据时才能写成确定性预期；无依据的影响关系记录为“待确认影响范围”，不得因此阻断其他已确认覆盖。

1. `操作反馈`：成功、失败、拦截或取消后是否存在提示、弹窗、按钮状态、页面停留或跳转。
2. `业务状态和数据`：目标数据是否创建、更新、删除、持久化、回显，以及业务状态如何变化。
3. `生效时间和范围`：立即、刷新后、重新进入、下一次业务或指定时间生效；是否影响当前业务、进行中业务和历史数据。
4. `角色、端和模块影响`：发起角色之外的其他角色、端、页面、列表、详情、流水、统计或下游模块是否需要观察。
5. `异常和恢复`：超时、依赖失败、部分成功、重复提交、重试、回滚、补偿和旧数据保留方式。
6. `并发和过程态`：操作发生时仍在进行的会话、审批、支付、编辑或读取请求如何处理；仅在功能存在相应风险时检查。对扣款或结算、依赖后台配置或商品状态、进房资格、角色权限、邀请或状态切换等高风险操作，不得只检查“变更后重新操作”的稳定终态，必须按第 3.2.1 节拆分过程时间点。

每个适用观察点必须执行以下三向判定：

- 需求、原型动态交互、标注、接口契约或用户确认已明确结果：生成或拆分为正式用例。已有明确结果却没有对应正式用例，属于“用例覆盖缺口”，不得改写成“需求待确认”。
- 该结果会影响业务验收，但证据缺少确定规则或来源冲突：生成独立的“需求待确认”，每条记录只要求做一个业务决定；不得使用“应该有提示”“通常会同步”等常见行为代替产品规则。
- 观察点与当前功能无关、没有实际风险或证据明确不适用：不生成用例，也不为了填满分类而制造待确认问题；必要时在覆盖清单记录不适用依据。

静态截图未展示操作后的瞬时状态，不等于原型没有定义。判定证据缺口前必须继续检查原型交互脚本、动态状态、便签、标注和提示文案。提示形式或文案没有依据时，只询问待确认规则，不得编造具体 Toast、弹窗或文案。

### 3.2.1 过程态与并发变更覆盖

过程态用于验证同一业务对象在一次操作尚未完成时发生状态或配置变化后的处理边界，不能用“刷新页面后再操作”替代。仅对存在实际竞争风险的操作执行，避免机械扩大用例。

1. **识别适用操作**：扣款、返奖、结算、库存或商品可用性、后台开关和配置、直播场次状态、进房资格、账号或房间权限、邀请处理、审批或编辑提交等操作，均应检查外部变化是否可能改变本次操作是否可继续、是否成功、数据归属或历史记录。
2. **按时间点检查**：对每项适用操作至少判断以下四个时间点是否存在独立业务结果：`操作开始前已变化`、`客户端已发起或服务端处理中发生变化`、`本次业务完成后发生变化`、`刷新、重进或重试后的状态`。只有条件、处理边界或可观察结果不同，才拆成独立用例。
3. **以业务提交边界为准**：不得把“打开面板”“点击按钮”“客户端发出请求”“服务端受理”“扣款”“状态落库”“页面回显”擅自认定为同一个完成时点。来源明确边界和结果时，按该边界生成正式用例；只明确变化前后稳定结果而未定义处理中请求的受理、扣款、回滚或反馈规则时，生成独立“需求待确认”。
4. **明确观察与归属**：过程态用例的前置条件可使用后台、接口或测试工具制造变更，但当前端操作步骤只能写目标端实际入口；预期结果只验证当前端可观察结果或已有证据明确的关联记录。其他端、接口或数据层的核对位置按第 2.2.1 节归属，不得伪装成当前端入口。
5. **覆盖不等于假设**：同一对象在操作过程中被下架、改价、关闭、结束、禁言、拉黑、踢出、取消权限或处理另一条邀请时，若资料没有给出本次请求的最终结果，不得默认“失败且不扣款”“继续成功”或补写具体提示。待确认问题必须单独询问一个边界，例如“服务端已受理赠送请求后礼物下架，本次赠送是否完成”。
6. **去重要求**：已覆盖“变更后刷新再操作”“已完成记录保留”不等于覆盖处理中边界；反之，若来源明确相同处理结果且没有独立观察点，应合并并在 `semantic-dedup-review.json` 记录时间点包含关系。

### 3.2.2 移动 App 生命周期与系统中断覆盖

本节仅适用于本次目标端是移动 App，且功能依赖持续会话、直播或实时音视频、摄像头或麦克风、网络连接、系统权限或交易回调中的至少一项。纯静态页面、普通离线表单及无相关原生能力的功能，不得为满足分类而生成此类用例。

1. **区分中断事件和 App 状态**：至少按实际风险分别判断切换后台/返回前台、锁屏/解锁、用户显式关闭、系统回收或崩溃后重启、来电或其他音频焦点中断、网络短暂中断或网络类型切换、运行中撤销摄像头或麦克风权限。不得把“退到后台”“关闭 App”“进程被系统终止”和“崩溃”视为同一事件；蓝牙或有线耳机插拔、画中画和系统通知只在产品明确支持或功能确有依赖时检查。
2. **按角色和会话分别建模**：直播、连麦、语音房等实时功能至少区分主播、观众和连麦参与者；需要同时观察本端和对端时，分别记录各自可观察的会话、画面、声音、操作权限和最终状态。不能用观众恢复结果推定主播推流结果，也不能用一方连麦状态代替另一方状态。
3. **覆盖中断前、中断中和恢复后**：对每个适用事件检查中断发生前的操作状态、中断期间的本端可操作性和外部业务变化、回到前台或重启后的会话恢复、数据同步、重连或结束状态。用户离开期间发生的关播、权限关闭、踢出、禁言、商品下架、邀请失效或交易回调，应按本端恢复后的最终可观察状态单独评估。
4. **保护交易和消息一致性**：中断前后存在赠送、购票、充值、评论、邀请处理或管理操作时，必须按第 3.2.1 节核对请求是否被受理、是否只处理一次、余额或记录是否重复，以及恢复后的展示是否遗漏或重复。不得把“重新进入后看到页面”当作交易、消息或实时状态已正确同步的证据。
5. **明确证据边界**：只有需求、原型动态交互、接口契约、当前实现的完整调用链或用户确认明确给出处理结果时，才生成正式用例。资料只说明网络重连、直播结束或权限限制而未定义后台、来电、锁屏、进程终止或恢复边界时，分别写入独立“需求待确认”；不得默认后台必然关播、来电必然静音、回前台必然自动恢复，或编造重连时限和提示文案。
6. **控制组合与去重**：先建立“角色/会话状态 -> 系统事件 -> 恢复动作 -> 观察结果”的覆盖映射。同一规则在 iOS、Android、不同网络类型或多种中断入口下确实具有相同触发条件、处理结果和观察点时合并为一个用例；只有平台能力、来源规则或可观察结果不同才拆分。系统版本、设备型号和网络环境作为执行记录或兼容性条件保留，不得替代业务规则或无依据扩展用例数量。

## 4. [SCHEMA-01] 统一 JSON 与 Excel 字段

结构化 JSON 根节点必须是对象，并包含：

- `测试用例`：可执行测试用例数组。
- `需求待确认`：无法确定预期规则的问题数组；没有问题时使用空数组。

### 4.1 功能测试用例字段

Excel 的“功能测试用例”工作表固定使用以下 15 列：

`序号, 用例编号, 功能模块, 功能结构, 用例类型, 优先级, 用例描述, 验证用例子项, 前置条件, 操作步骤, 预期结果, 流程编号, 测试结果, 测试人员, 备注`

要求：

- `序号`：从 1 连续递增。
- `用例编号`：同一功能模块只使用一个稳定前缀，模块内连续编号。
- `流程编号`：位于“预期结果”之后；仅跨端或跨模块流程用例填写稳定且唯一的流程编号，同一业务流程的拆分用例填写相同编号；普通单模块用例留空，不得为凑编号强行建立流程。
- `用例类型`：只能是 `功能需求`、`业务流程`、`逻辑校验`、`异常用例`。
- `优先级`：只能是 `P0`、`P1`、`P2`、`P3`。
- `用例描述`：必须以“验证”开头，用一句可直接扫读的话说明本条用例的场景和测试意图；只保留区分本条用例所需的角色、关键条件、动作或状态，不抄写完整步骤和预期结果。
- `验证用例子项`：使用简短名词短语写本条用例唯一的验证维度或对象，例如“评论入口”“礼物名称回显”；不重复抄写整个用例描述。去除序号、空格和标点后，不得与用例描述正文或预期结果完全相同；它可以与预期结果指向同一观察点，但不能直接复制完整结果句。
- 同一验证维度在不同输入、必要条件或边界下可以使用相同子项；不得为满足字符串唯一性而截断名称或追加无业务含义的尾词。冲突和重复判断必须包含必要条件、关键输入、执行角色、操作及观察结果。
- `前置条件`：只保留执行角色、初始业务状态和本条用例必需的测试数据；进入页面、点击按钮等本次操作写入“操作步骤”。
- `操作步骤`：按执行顺序只写完成本条验证所需的具体动作和对象，不写已具备的条件，不提前描述结果。
- `预期结果`：JSON 中必须是只包含 1 个字符串元素的数组；Excel 中只展示这 1 个有依据、可观察且可以直接判定通过或失败的结果，不写“检查是否”“确认是否”等执行指令。
- `前置条件`、`操作步骤`、`备注`：JSON 中使用字符串数组，Excel 中按顺序换行编号。
- `测试结果`：默认 `未测`，允许 `通过`、`不通过`、`阻塞`、`不适用`。
- `测试人员`：默认留空。
- `备注`：按来源文件各写一条追溯记录，同一文件的多个位置合并；再保留稳定规则标识、必要限制和“未动态验证”等交付边界。不得重复业务步骤、预期结果或固定长说明。历史用例编号可以作为追溯，但不得成为唯一来源。跨端或跨模块拆分用例还必须写明当前流程阶段和共同业务对象，流程编号填写在独立列中。

### 4.2 需求待确认字段

Excel 的“需求待确认”工作表固定使用以下 20 列：

`问题编号, 需求组编号, 父问题编号, 追问触发条件, 阻塞等级, 功能模块, 具体场景, 问题分类, 待决策问题, 可选方案, 测试建议, 产品结论, 结论补充, 已知依据, 影响范围, 已有用例编号, 确认后待补用例, 负责人, 期望确认时间, 确认状态`

- `问题编号`：每个决策点必须唯一。根问题使用 `Q-003`；一级追问使用 `Q-003-01`；确有连续条件链时允许二级追问 `Q-003-01-01`。默认只使用一级追问，超过二级时应拆成新的需求组。
- `需求组编号`：使用稳定且唯一的 `RQ-003` 格式。同一父需求或同一证据缺口下的相关问题填写相同需求组编号；同组只表示业务关联，不自动表示回答依赖。
- `父问题编号`：仅当子问题是否适用或可选方案会随某个前置结论变化时，填写其直接父问题编号；只是先后讨论、引用同一资料或属于同一场景的问题保持并列并留空。父问题必须存在于同一需求组，不得指向自身、后代或形成循环依赖。
- `追问触发条件`：子问题必须写明父问题的具体选项或可观察业务条件，例如 `Q-003 选择 B 后`、`Q-006 选择 A 或 C，消息未进入公屏时`；根问题和并列问题留空。不得只写“父问题确认后”“范围明确后”，也不得使用“视情况而定”等无法判断的条件。
- `阻塞等级`：只能是 `阻塞测试`、`部分阻塞`、`不阻塞`。`阻塞测试` 表示没有结论就无法形成核心业务预期或继续关键测试；`部分阻塞` 表示只影响部分场景、边界或异常测试；`不阻塞` 表示不影响当前主要测试，可在版本验收前确认。
- `具体场景`：使用简短文本写明角色、业务状态、触发动作和必要对象范围，使产品无需重新查找问题发生条件；不得使用“关键操作”“所有写操作”“跨端模型”等未列举对象的宽泛概念。
- `问题分类`：每条记录只能选择一个主要分类，允许值为 `需求范围`、`业务规则`、`角色与权限`、`流程与状态`、`字段与数据校验`、`计算与统计口径`、`异常处理`、`跨端与跨模块一致性`、`配置和历史数据影响`、`交互与文案规则`。
- `待决策问题`：必须是产品可以直接回答的单一决策问题，并明确询问对象、动作、适用端或适用操作。一行不得同时询问两个独立规则，不得使用“以及”“同时”或并列编号串联多个决定；条件依赖的问题拆成独立记录，并通过“父问题编号”和“追问触发条件”建立显式关系，不得只在场景文字或编号前缀中暗示。
- `可选方案`：JSON 中使用包含 2 至 4 个方案的字符串数组，Excel 中按 `A.`、`B.`、`C.`、`D.` 换行展示。同一行的方案必须处于同一决策维度、彼此不能同时成立，并共同覆盖主要业务选择；客户端防重复、服务端去重、提示形式等可以并存的控制不得作为同一组选项。
- 方案必须在被选中后直接形成可测试规则。禁止使用“固定时间”“统一上限”“中间档”“短暂时间窗”等未给具体值的占位参数；应写明具体候选值、以可读取的配置为唯一依据，或拆出有明确触发条件的参数问题。选择方案后仍缺决定结果的参数时，不得将问题标记为 `已确认`。
- 禁止把“各功能单独定义”“另行定义”“视情况处理”作为逃生选项。确需分功能处理时，方案中必须列出完整操作分组及各组规则，或建立可追溯的子问题/决策矩阵；未形成这些记录的方案不算可选结论。
- 涉及旧数据、进行中业务或新旧规则兼容时，每个方案必须同时说明旧数据范围、新规则从何时或对哪些对象生效，以及旧规则何时退出；任一边界缺失时拆成独立待确认问题。
- `测试建议`：测试根据证据一致性、风险、可测试性和实现复杂度推荐一个方案并说明简短理由，但不得代替产品填写最终结论。
- `产品结论`：初次交付默认留空，是产品经理主要填写列；只能单选 `A`、`B`、`C`、`D`、`其他`，不得重复抄写完整方案文本。
- `结论补充`：初次交付默认留空；选择 `其他` 时必须填写具体规则，选择 `A`、`B`、`C` 或 `D` 时仅在需要补充适用范围、生效时间等信息时填写。
- `已知依据`、`影响范围`、`已有用例编号`、`确认后待补用例`：JSON 中使用字符串数组，Excel 中按顺序换行展示。已知依据只保留支持问题或形成冲突的关键信息；影响范围必须列出具体角色、端、页面、操作或数据对象，不得只写“相关功能”“所有操作”。
- `已有用例编号`：只填写工作簿中已存在且可核对的用例编号或连续编号区间，例如 `LIVE-030`、`LIVE-030 至 LIVE-035`；没有准确编号时使用空数组，不得混入场景名称。
- `确认后待补用例`：只填写规则确认后需要新增、补写或重审的用例范围名称；没有待补范围时使用空数组，不得冒充已有编号。两列至少一列非空。
- `负责人`：只能是 `产品`、`交互`、`技术`、`多方确认`。纯技术可行性或技术时效问题不得全部转交产品；涉及业务选择与技术约束时使用 `多方确认`。
- `期望确认时间`：填写有依据的日期或项目里程碑，例如 `进入对应功能测试前`、`本轮回归前`、`版本验收前`；没有项目排期依据时使用里程碑，不得编造日期。
- `确认状态`：根问题和并列问题初次交付为 `待确认`；子问题初次交付为 `待前置结论`。允许 `待前置结论`、`待确认`、`确认中`、`已确认`、`无需处理`。父问题结论触发追问时将子问题改为 `待确认`；父结论使追问不适用时改为 `无需处理`。
- 排序时先计算需求组内所有问题的最高阻塞等级，并按 `阻塞测试`、`部分阻塞`、`不阻塞` 排列需求组；组内使用父问题优先的树形前序排列，父问题必须紧邻并先于全部子问题，同级问题按问题编号排序。不得再次按单行阻塞等级打散父子关系。
- 规则确认后，由测试将结论转换为正式测试用例并保留问题编号追溯；`确认状态` 由测试或项目负责人维护，不要求产品重复填写。

## 5. 优先级口径

优先级表示测试执行顺序，不表示缺陷严重程度：

- `P0`：最小冒烟集；核心入口和主交易/主流程，不通过时无法继续关键测试。
- `P1`：核心业务规则、权限、状态转换、金额或统计计算、关键边界和异常恢复。
- `P2`：次要功能、常见替代路径、一般边界和低影响异常。
- `P3`：低频、兼容性、健壮性或明确低风险场景。

不得因为场景描述复杂就提高优先级，也不得把所有主流程都标为 P0。

## 6. 风险驱动测试设计

根据功能实际情况选择以下覆盖维度，不机械凑数：

- 主成功流程和真实用户任务。
- 替代流程、取消、返回和中断恢复。
- 角色、权限、会话失效和数据范围。
- 状态来源、触发动作、目标状态和终态限制。
- 必填、格式、唯一性、枚举、空值和非法类型。
- 等价类、最小值、最大值、零、负数、精度、时间边界和超长输入。
- 重复点击、重复请求、幂等、并发和乱序；仅在业务或实现存在相应风险时生成。
- 超时、依赖失败、部分成功、重试、回滚和补偿。
- 移动 App 的前后台切换、锁屏、进程终止、系统音频中断、网络切换、运行中权限变化及恢复后的会话和数据一致性；仅在第 3.2.2 节适用时覆盖。
- 金额、数量、统计、舍入、去重、分页和跨页面一致性。
- 跨端状态流转；只写有证据的页面、字段和结果。

每条用例只能有一个预期结果，该结果必须是一个可独立观察和判断的业务结果。

- 同一次操作需要验证页面跳转、状态变化、提示、数据记录或其他端结果时，分别拆成不同用例。
- 不得通过连接词、分号、换行或编号，把多个独立结果合并到同一个预期结果字符串中。
- 跨端状态流转按观察端拆分用例；每条用例只保留该端的一个预期结果。
- 拆分后的用例可以复用前置条件和操作步骤，但“验证用例子项”和“预期结果”必须对应本条唯一观察点。
- 单结果拆分不是去重完成标志。拆分后必须删除与本条唯一结果无关的操作步骤，并按第 11 节重新检查业务规则归属、条件必要性、状态包含和语义重复；不得让拆分动作把一条重复规则扩展成多条重复用例。

### 6.1 跨端与跨模块流程

- 只有证据表明业务需要经过两个及以上端或模块时，才建立跨端或跨模块流程，不根据常见产品行为臆造链路。
- 跨端流程必须来自 `STATE-01` 的业务对象状态转换基线；每条流程使用稳定且唯一的流程编号，每个端的场景再绑定状态转换标识和流程阶段。不得用三个端中相似的页面名、结果文字或历史编号代替状态连续性。
- 同一流程拆分出的用例必须在“流程编号”列填写相同编号；前置条件写明可识别的共同业务对象、当前来源状态，以及会影响数据范围的组织、租户、地区或时间条件，不展开无关字段。
- 按证据覆盖触发动作、中间状态、目标端终态以及确有风险的失败恢复；其他端已完成动作只写成当前来源状态，本端只执行实际归属于本端的动作。无法确定的环节进入“需求待确认”或 `待补转换`，明确不适用的环节记录不适用依据。
- 异步同步、回调或延迟生效场景必须依据需求、接口契约、系统配置或用户确认写明等待时限或终态判断条件，并在操作步骤中写明刷新、重新进入或轮询动作。没有时效依据时不得编造“立即同步”或具体等待秒数，应写入“需求待确认”。
- 重试、补偿、重复消息和乱序处理只在证据或实际依赖风险存在时生成；每条用例仍只验证一个观察端的一个业务结果。

## 7. 页面类型拆分

- 列表页：筛选、排序、分页、空态、列表字段、操作入口、数据范围和聚合口径。
- 表单页：完整成功提交、必填、格式、边界、重复数据、取消、保存后回显。
- 详情页：字段来源、只读限制、状态、操作入口、历史快照和空值展示。
- 配置页：保存、读取、生效范围、历史数据影响和业务引用。
- 状态流转页：来源状态、触发条件、目标状态、失败恢复和终态限制。
- 财务/支付页：金额公式、精度、退款上限、多次退款、流水、回调、幂等、结算和余额一致性。

页面入口用例不能因存在业务用例而一律删除。登录、路由、权限或核心冒烟需要入口验证时应保留。

## 8. 字段区域与表单规则

- 先区分筛选区、列表表头、列表行内组合字段、详情字段和弹窗字段，不得混写。
- 字段展示用例只列真实存在的字段；筛选条件另写筛选用例。
- 文本是否截断、换行或显示省略号必须以设计说明为依据，不统一要求“不截断”。
- 表单成功用例应覆盖本次流程所需的全部业务字段；字段级校验应拆分验证。
- 必填范围或提示文案不明确时，进入“需求待确认”。

### 8.1 测试数据准备粒度

测试数据的详细程度必须与被测功能对数据的依赖程度匹配，不得对所有用例套用同一种详细模板。

- 简单新增、编辑、删除、入口和字段展示用例，只写完成操作所需的最小有效数据；不逐项罗列与本条验证无关的字段值。
- 字段级校验只具体说明目标字段；不影响本条结果的其他必填字段可以统一写“填写合法值”或“保持已有合法值”。地区、币种、组织、时间、SKU、状态等关联字段会影响计算、权限、状态或数据范围时，必须写明必要的关联条件。
- 普通业务用例不得直接保留 `yyyyMMddHHmmss` 等技术格式串，也不得引用未实际提供的虚构文件名。确需避免重名时，写“使用一个未被占用的名称”；确需指定文件时，写明可准备的文件类型、大小或实际数据位置。
- 聚合统计、金额和其他计算类用例必须充分准备可复算的数据，包括统计周期、业务状态、统计维度、纳入数据、排除数据、边界数据、原始数值、计算公式和最终数值。
- 报表筛选和数据范围用例只准备能够区分纳入与排除结果的最小数据集，并写明预期记录集合或数量；报表字段展示、导航、下载入口等非计算用例使用最小有效数据，不强制提供公式和完整原始数据。
- 审批、状态流转和跨端一致性用例按验证需要写明角色、共同业务对象、来源状态、目标状态、变更前数据、变更后数据和观察端，不扩展无关字段。
- 只有当具体数据能影响预期结果、边界判断、数据唯一性或执行可复现性时才展开描述；否则使用简洁的合法数据条件。

### 8.1.1 业务对象名称与数据别名

- 用例编号、流程编号、问题编号、需求组编号和规则/同步日志编号属于结构化追踪标识，按各字段规则保留，不得改写为业务名称。
- 礼物、账号、主播、直播场次、订单、交易记录等测试业务对象应优先使用执行人员可直接识别的名称。为了跨步骤、跨端或日志追踪而设置的数据别名，只能作为名称的辅助信息，不得用裸编码代替名称。
- 同一条用例中，业务对象首次出现在 `前置条件`、`操作步骤` 或 `预期结果` 时，统一写成 `可识别名称（数据别名：CODE）`；后续再次出现时只写可识别名称。示例：`礼物“星光”（数据别名：GFT-LIVE-03）`，后续写 `“星光”`。
- 可识别名称必须来自原型、需求、接口、Mock、现有可准备数据，或由用户、测试负责人明确确认的数据准备约定。生成者不得把自己临时拟定的名称记录为“本次测试数据准备约定”，也不得使用引号把对象状态、权限或预期行为包装成名称，例如不得自行生成“免检账号B”“灰度测试主播”“平台关播测试场次”等名称。
- 输入材料没有给出可识别名称时，必须使用有证据的 `对象类型/业务关系/关键状态（数据别名：CODE）` 表达，后续写 `该对象`、`该主播`、`该运营账号`、`该直播场次` 等指代。例如：`已启用的运营账号（数据别名：OP-LIVE-02）`，后续写 `该运营账号`。对象描述只能包含本条用例已明确的条件，不得把待验证结论写进描述。
- 页面标题、直播标题、订单备注等字段值与承载该字段的业务对象必须分开表达；不得因为某场直播的标题为“深夜聊天局”，就把直播场次本身命名为“深夜聊天局”。应写成 `历史直播场次（数据别名：LIVE-SESSION-002）的开播标题为“深夜聊天局”`。
- 实际系统生成或接口返回的主键、订单号、场次号等仅在确实可准备、录入、查询或核对时使用，并明确写为实际 ID 或实际单号，不得与测试数据别名混淆。
- `备注` 中允许为追溯保留业务对象的数据别名，但也必须随来源名称或对象描述解释，不得只写业务对象裸编码。正式执行字段中不得出现未解释的业务对象裸编码。输出前必须扫描 `前置条件`、`操作步骤`、`预期结果` 和 `备注`，确认每个业务对象数据别名在本条用例首次出现时已经随名称或对象描述解释。
- 中文名称、字段值或数据别名说明后的助词和动作词应直接衔接，不得在右引号 `”`、右全角括号 `）` 与后续中文之间保留多余空格。输出前必须扫描并清理此类显示问题，但不得删除英文、数字或实际语义需要的空格。

### 8.2 前置条件最小化与单分支规则

- 每条用例的前置条件和操作步骤只能描述一条确定的业务执行路径。不得使用“场景 A / 场景 B”“条件一 / 条件二”或“或”并列可替代的角色、页面、入口、业务关系、来源状态、输入类别或操作方式；需要覆盖多个分支时，必须拆成不同用例。
- 前置条件采用“最小充分集”：每个条件必须直接决定本条操作可执行、触发本条验证规则、排除会改变结果归因的其他独立原因，或使结果可以复现。删除某个条件后操作和预期仍完全成立时，该条件属于冗余条件，必须删除。
- 前置条件必须与“验证用例子项、操作步骤、预期结果”使用同一业务对象、关系和状态。只出现在前置条件中，后续操作和预期均不依赖的对象或状态属于孤立条件，不得保留。
- 验证某一种限制、权限或关系时，应在必要范围内明确排除其他会产生相同结果的独立原因。例如验证直播间黑名单限制时，需确保不存在账号拉黑；验证账号拉黑限制时，需确保目标用户不在直播间黑名单。排除条件用于保证结果可归因，不视为无关数据。
- 同一用例可以准备多个必须同时存在的对照数据，例如筛选用例同时准备一条应纳入记录和一条应排除记录；必须明确写成“同时存在”或分别列为条件，不得写成供执行者任选的 A/B 分支。
- 为同一次业务操作拆分多个观察结果时，可以复用确实共同需要的前置条件和操作步骤。不同验证点出现完全相同的复杂前置条件时，交付前必须复核每个条件是否都对各用例必要；不能因为复制方便而整段照搬。

## 9. 计算与统计规则

计算类用例必须具备：

1. 在前置条件中写明指标或金额定义、数据范围、过滤条件、精度、舍入口径和具体测试数据。
2. 在操作步骤中写明触发计算和查看结果的动作。
3. 在唯一的预期结果中写明公式、代入过程和一个最终数值。
4. 跨页面、流水或余额一致性分别拆成其他用例，每条仍只保留一个预期结果。

缺少任一决定最终结果的规则时，不编造数值，写入“需求待确认”。

计算要求按本条观察点是否涉及数值运算判断，不按“逻辑校验”类型一律套用。计算测试数据必须明确业务变量、原始值、单位、数据范围及纳入条件，按有来源的公式独立复算；禁止在未匹配公式时补写通用算式。只验证展示上限、省略或字段可见性的用例不得附加无关计算结果。

## 10. [LANG-01] 语言和步骤规范

1. **字段职责**：`功能结构` 只负责归类；`用例描述` 回答“这条用例验证什么场景”；`验证用例子项` 回答“唯一验证维度是什么”；`前置条件` 回答“执行前必须具备什么”；`操作步骤` 回答“本次具体做什么”；`预期结果` 回答“看到什么即可判定”；`备注` 只负责追溯和必要限制。
2. **整体可读性**：生成和复核时必须连读上述字段，确保执行人员一眼能识别角色、场景、动作和判断标准。精简以删除字段间重复、无业务意义的套话和非必要条件为准，不以机械删词、截断句子或统一字数为合格标准；不得因缩短文本删除决定执行或结果的对象、条件、数据、数量、时限和状态。
3. **前置条件边界**：前置条件只保留角色、初始业务状态和必要测试数据。页面入口与本次进入、点击、查看、切换等动作写入“操作步骤”；不得把“使用某身份进入某页”同时当作角色和操作塞入前置条件。每个数组元素只写一个条件。
4. **步骤边界**：操作步骤按执行顺序写具体动作和对象，只保留触发本条唯一结果所需的步骤；不得重复前置状态、夹带预期结果或增加与本条观察点无关的查看动作。按钮、字段、状态和提示文案优先使用证据原文。
5. **结果边界**：预期结果直接写可观察的对象和最终状态，不写“验证、检查、核对、确认、查看是否”等测试指令，不复述操作步骤；缺少确定观察标准时按 `CASE-01` 处理。
6. **备注边界**：同一来源文件只保留一条来源记录并合并位置；除稳定规则标识外，只保留实现推导、未动态验证、流程阶段或其他会影响执行和解释的必要限制，不重复用例正文。
7. **禁止占位**：不得使用“业务规则”“操作结果”“执行目标操作”等通用占位内容代替具体场景、验证维度或操作。目标端入口、动作或观察方式缺少证据时，按 `CASE-01`、`ROLE-01` 进入需求待确认，不得用占位词补齐正式用例。
8. **含糊表达**：机器规则区列出的含糊词在缺少明确对象、位置、数据、数量、时限、状态变化或观察标准时不得单独使用。示例数值和账号只说明表达方式，不构成业务证据；具体值必须来自当前证据或已确认的数据准备约定。
9. **词表边界**：动作词和结果词只规范已有证据支持的表达，不构成页面、入口、权限、状态或业务行为证据。`当前`、`有效`、`其他`、`正确` 等词可以作为正式字段、状态或需求原文的一部分，但不能单独承担结果判断。
10. **单一执行来源**：下方机器规则区是动作词、含糊词和禁止占位词的唯一清单。生成时必须读取该区域；`scripts/validate-testcase-json.mjs` 必须从该区域加载并校验，不得在脚本中复制维护另一份词表。

## 11. [DEDUP-01] 多来源合并与去重

重复判断必须以业务规则和可观察结果为中心，不能只看标题、编号、功能结构、页面名称或原文是否完全一致。`功能结构` 只是归类字段，不足以证明两个验证点相互独立。

### 11.1 规则归一化

- 生成用例前，将证据索引中的明确规则归一化为：`稳定规则标识 + 业务对象 + 共同业务对象 + 执行角色 + 适用角色和端 + 触发动作 + 必要条件 + 来源状态 + 目标状态或可观察结果 + 来源`。存在生命周期时再按 `STATE-01` 生成稳定的状态转换标识和流程编号。一条规则只表达一个执行角色、一个动作和一个可观察结果；稳定规则标识由这些字段形成的归一化业务键生成或沿用，不得因文件顺序、数组位置或用例排序变化。规则、状态转换和流程标识只用于任务过程和追溯，不新增正式 JSON 或 Excel 字段；跨端用例继续使用已有“流程编号”列。
- 同一规则在当前需求、多个页面、批注、Mock 或代码中重复出现时，合并到同一规则标识下。历史用例只能在规则清单完成后绑定该标识，不得参与定义规则。页面数量、批注数量、历史用例数量和来源数量只增加证据或追溯，不自动增加用例。
- 对房型、角色、权限、流程阶段、开关和业务状态建立有证据的 `包含`、`互斥`、`前置` 或 `无影响` 关系。例如只有证据明确“连麦仅支持普通房”时，才能记录 `连麦中 -> 普通房`；不得根据常见产品行为自行建立关系。

### 11.2 独立验证点与条件覆盖

对具有相同业务对象、角色和端、关键操作及可观察结果的候选用例，按以下顺序判断：

1. **条件删除测试**：逐项删除候选用例比基础用例多出的前置状态或限制；删除后操作仍可执行且预期完全不变时，该条件是冗余条件，不能据此建立独立用例。
2. **规则覆盖测试**：规则 A 的必要条件被规则 B 完全包含，且两者的业务对象、角色和端、关键操作、状态去向或可观察结果相同时，B 是 A 的状态子集；默认保留条件更基础的用例，把 B 的来源和适用说明合并到备注。
3. **差异保留测试**：附加状态导致入口、可执行动作、目标状态、提示、数据结果、观察端或恢复方式发生有依据的变化时，保留独立用例，并在去重复核记录中写明唯一差异。仅修改标题、功能结构、页面名称或前置状态措辞不能证明差异。
4. **实现变体例外**：业务结果相同，但证据表明不同状态使用独立入口、组件或处理分支，或者用户明确要求分别回归时，可以保留为状态变体；必须标记为 `实现变体` 或 `用户指定覆盖`，写明不同路径和风险，不能伪装成新的业务规则。仅共享代码在不同页面被调用，不足以自动保留重复用例。
5. **无法判断**：证据不足以确认状态关系或独立实现路径时，不得按常识自动合并或删除；记录为 `待人工复核`，隔离涉及的候选并转入“需求待确认”，其他候选继续处理。只有无法定位涉及哪些候选、导致整个候选集一致性不可判断时，才阻断最终 JSON 和 Excel。

### 11.3 拆分后和增量生成去重

- 单预期结果拆分后必须再次执行第 11.2 节。拆分出的每条用例只保留触发本条结果所需的步骤；例如预期只验证入口置灰时，不得继续保留“点击入口”作为无关步骤。
- 增量生成或重建时，先从当前证据建立规则清单并生成候选用例，再将已有用例绑定到当前稳定规则标识，判断继续有效、需要重写、合并、已被替代、应当废弃或待人工复核。不得从已有用例数组复制出候选，不得因为已有用例编号不同就默认保留，也不得把会随排序变化的 `LIVE-xxx` 等交付编号黑名单作为唯一删除机制。
- 去重至少比较：`稳定规则标识/状态转换标识/共同业务对象 + 适用角色和端 + 有效必要条件 + 关键输入和操作 + 状态去向或可观察结果`。先按流程、状态转换、模块、执行角色、动作类别和结果类别建立业务键桶，只在桶内执行相似度比较；跨桶关联由依赖索引复核。同一状态转换按不同观察端拆分的场景不得互相合并，单端内重复观察结果仍须合并。标题、验证用例子项和完整字符串相等检查只能作为第一层快速检查，不能单独得出“业务语义重复为 0”的结论。
- 同一业务规则或同一证据缺口的待确认记录应跨页面、跨模块合并来源和影响范围，但一个记录仍只能要求做一个决定；角色、适用范围、决策问题或可选结论不同的记录必须拆分。同属一个父需求的记录使用相同需求组编号；只有回答上存在直接依赖时才填写父问题编号和追问触发条件，不得仅凭相同编号前缀推断父子关系。

### 11.4 去重复核产物

每次生成、增量修订或重审测试用例时，在本次任务 `work/` 目录保存 `semantic-dedup-review.json`，至少记录：

`稳定规则标识, 候选用例追溯, 归一化业务键, 基础条件, 附加条件, 状态关系, 关键操作, 可观察结果, 判定, 保留或合并目标, 判定理由, 证据`

- `判定` 只能是 `保留`、`合并`、`实现变体`、`用户指定覆盖` 或 `待人工复核`。
- 被合并记录必须指向实际保留的规则或候选用例，并说明合并了哪些来源；不得只从最终数组中静默消失。
- 报告中的重复数量和最终用例数组必须一致；只执行标题、验证点或完整字符串查重，不得把结果记为已完成业务语义去重。

## 12. 旧 10 字段兼容规则

旧 JSON 只允许以 `历史参照` 角色进入格式转换和历史比较，不得作为当前业务证据或候选用例数据源。旧字段转换后的记录仍是历史记录，只能写入 `historical-case-comparison.json` 或专用迁移结果；不能直接写入当前正式用例数组。转换关系如下：

- `module` → `功能模块`
- `page` → `功能结构`
- `type` 或 `Type` → `用例类型`
- `priority` 或 `Priority` → `优先级`
- `title` → `用例描述`
- `page_01` 与标题中的具体场景 → `验证用例子项`
- `precondition` → `前置条件`
- `step` → `操作步骤`
- `expected_result` → `预期结果`
- `Remarks` → `备注`

转换器补充 `序号`、`用例编号`、`流程编号`、`测试结果=未测` 和空的 `测试人员`。旧记录备注中已有明确流程编号时，将其迁移到“流程编号”字段；没有明确流程证据时该字段留空，不得自行推断。旧记录中明确包含“待确认”或“待验证”的事项，应同步写入“需求待确认”；不得仅隐藏在备注中。

### 12.1 旧需求待确认兼容规则

- 旧 8、9、15、18 或 19 字段待确认记录只允许作为输入，不得直接作为新交付格式。
- 旧 `功能结构` 转换为包含角色、状态和触发动作的 `具体场景`；证据不足时至少保留原功能结构，不得虚构角色或状态。
- 旧 `待确认事项` 和 `缺失信息` 中包含多个独立决定时必须拆分；拆分记录使用稳定问题编号，不得把多个决定改写成一个宽泛“策略”。转换时根据业务来源补充需求组编号；仅在文字明确存在前置结论依赖时建立父子关系，不能只因编号相近、排列相邻或场景相关就推断为追问。
- 转换器根据对测试执行的实际影响填写 `阻塞等级`，生成 2 至 4 个互斥 `可选方案` 和一条明确的 `测试建议`，但 `产品结论` 和 `结论补充` 保持空字符串。
- 旧 `已知依据` 和 `影响用例` 分别转换为字符串数组；旧 `影响用例` 中可核对的编号迁移到 `已有用例编号`，描述性范围迁移到 `确认后待补用例`，不得继续混写。补充 `需求组编号`、`父问题编号`、`追问触发条件`、`影响范围`、`负责人`、`期望确认时间` 和确认状态。没有真实父问题时状态为 `待确认`，存在未确认父问题时状态为 `待前置结论`。

## 13. [EXCEL-01] Excel 交付标准

- 测试用例统一保存到 `outputs/<项目名称>-case/`；`<项目名称>` 使用正式需求、原型说明或用户确认的实际项目名称，目录名固定追加 `-case` 后缀，不得使用任务 ID、线程 ID、UUID、日期或“项目名称”等占位文本作为目录名。
- 项目名称无法从证据中确定时，必须先写入“需求待确认”或向用户确认，不得自行编造目录名。
- Excel 测试用例文件名固定使用 `<端名>-<模块名>-<日期yymmdd>-<编号>.xlsx`，例如 `用户App-直播模块-260827-001.xlsx`。
- `端名` 和 `模块名` 使用正式需求、原型说明或用户确认的名称；日期使用文件生成日期的六位 `yymmdd` 格式。
- `编号` 固定为三位数字；同一项目目录内相同“端名 + 模块名 + 日期”组合从 `001` 连续递增。生成新文件前必须扫描已有编号并使用下一个编号，不得覆盖已有文件。
- 同一项目的不同端、模块、日期和版本通过文件名区分，继续保存在同一个项目目录中。
- 工作簿固定包含“功能测试用例”“需求待确认”和“产品决策概览”三个工作表。“需求待确认”是产品决策的唯一可编辑数据源，“产品决策概览”只通过公式汇总，不得复制一套可编辑结论。
- “功能测试用例”和“需求待确认”均冻结首行、启用筛选、使用表格样式、自动换行和垂直居中。“需求待确认”还应冻结便于定位问题的左侧关键列；“产品决策概览”冻结标题区并默认作为打开工作簿时显示的工作表。
- 列宽和行高按内容调整并设置合理上限，确保主要内容可阅读。
- “功能测试用例”必须严格使用 15 列顺序；“需求待确认”必须严格使用第 4.2 节定义的 20 列顺序。
- “需求待确认”的“阻塞等级”“问题分类”“产品结论”“负责人”和“确认状态”列必须配置单选数据验证，选项使用第 4.2 节定义的允许值。
- “产品结论”和“结论补充”列使用明显但克制的可编辑底色；产品经理通常只填写“产品结论”，选择“其他”或需要限定适用范围、生效时间时再填写“结论补充”。
- “需求待确认”的关系字段必须保留。默认视图可隐藏功能模块、问题分类、已知依据、影响范围、已有用例编号和确认后待补用例等测试追溯列，但不得删除；用户取消隐藏后必须能够恢复全部信息。
- 子问题在视觉上使用轻量缩进或关系底色与根问题区分，并使用 Excel 分级显示默认折叠；父问题行必须保持可见，展开后子问题顺序和父子关系不得变化，不得通过删除或筛选隐藏子问题。
- “需求待确认”按需求组最高阻塞等级排序，组内按父问题优先的树形顺序排列；手工筛选或排序后仍能通过需求组编号和父问题编号恢复关系。
- “产品决策概览”至少汇总问题总数、当前可回答、待前置结论、确认中、已确认和无需处理，并按阻塞等级和负责人汇总当前待确认数量；所有可变数量必须使用公式引用“需求待确认”，与明细实时一致。
- 不得在正式交付工作簿中保留临时工作表、调试信息或公式错误。

## 14. [DELIVERY-01] 交付前质量门禁

交付前按下表分组检查。对应规则章节的全部条款均适用，本节只核对产物和结论，不重复定义细则。

质量门禁只检查准备进入正式交付的用例。已按 `GATE-01` 隔离并完整记录去向的问题项、需求待确认和候选测试场景可以随正式用例交付，不得因其存在而阻断不受影响的用例。

2. 每条正式用例可以追溯到当前稳定规则标识和哈希一致的当前证据；跨端或跨模块用例还必须追溯到状态转换标识和流程编号。历史文本、扫描结果、同步结果和状态转换基线没有替代原始证据定义业务规则。

4. 计算、异步、跨端、移动 App 生命周期和并发场景分别满足适用章节；跨端流程分别报告状态转换覆盖、目标端场景覆盖和实际执行结果，不适用时有依据，不机械增加用例。

7. 生成器只能将已复核的结构化用例设计渲染为正式字段；不得从未复核的自然语言片段猜测动作、补写观察位置或套用计算结果。规则清单中的设计须包含场景、子项、逐步角色与对象映射、观察位置和证据引用；复核结果绑定设计内容哈希，任何修改后须重新复核。这里的复核由生成执行者完成，不是要求用户逐条批准。

## 15. [CHANGE-01] 规则文件变更日志与回退

对 `AGENTS.md` 或 `Cem Kaner.txt` 的任何新增、删除、修改或回退，必须在同一次任务中同步追加到根目录 `规则文件变更日志.md`。

- 根目录只维护这一个规则变更日志，不得按日期、文件或任务另建其他规则日志。
- 日志采用追加方式维护；已有记录不得删除、覆盖或改写。日志记录本身有误时，追加一条更正记录。
- 每条记录必须包含连续变更编号、修改时间、用户要求或修改原因、涉及文件、修改位置、修改前原文、修改后原文和明确的回退方法。
- 修改前先读取日志并确定下一个变更编号；修改后核对文件实际差异与日志记录一致。
- 执行回退也属于一次新改动，必须追加新的回退记录，并引用被回退的变更编号。
- 未同步写入日志的规则文件改动视为未完成，不得交付。

`需求清单变更日志.md` 与本节的规则日志职责不同：前者记录项目 `context/`、MainBasis 需求文档及来源策略的同步变化，后者记录规则文件变化。两类日志均在根目录按各自职责保持唯一，不得按项目、日期或任务另建同类日志。
