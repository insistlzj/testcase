# 全局证据扫描指令

执行本指令前，先按 `新项目首次接入指令.md` 确认项目已经登记或符合旧项目兼容依据。接入状态为 `待确认` 或 `阻塞` 时不得启动正式全局证据扫描；首次接入确认后或首次使用旧项目兼容依据时，第一次扫描固定使用 `full`。

## 1. 目的与适用范围

本指令适用于生成、增量修订和重审测试用例前的项目证据扫描。目标是在不重复语义读取全部项目文件的前提下，保持目标模块与公共规则、管理后台、公会端、第三方及下游数据之间的关联完整。

本指令只扩大证据范围，不自动扩大用户指定的测试范围。其他端文件可以证明当前模块的配置来源、状态影响或下游结果，但除非用户明确要求，不据此生成其他端自身的模块用例。

项目配置全新生成模式时，按 AGENTS.md 的 BASIS-01 第 8 项执行；旧任务、旧用例、旧语义缓存及 archive 目录均不进入扫描业务输入，不用于检索词或覆盖候选。本轮归档后首次重建执行 full；完整保留当前原始资料和项目接入身份。

## 2. 固定产物

每个项目维护一个可复用的分层缓存：

```text
work/<项目目录名>-global-evidence-cache/latest.json
work/<项目目录名>-global-evidence-cache/layers/
```

每次生成任务保存独立快照：

```text
<本次任务work目录>/global-evidence-scan-result.json
```

任务快照不得只引用缓存路径，必须保存本次实际使用的扫描模式、项目指纹、证据基线、读取和复用范围及最终复核结果，使历史用例可以独立追溯。

`latest.json` 只保存各层输入哈希、Schema、产物哈希和当前指针；`layers/` 按 `inventory`、`evidence-atoms`、`normalized-rules`、`cases-history`、`workbook` 保存可复用产物。项目级缓存是可删除的加速数据，历史任务快照和项目接入记录不是缓存。清理只作用于已判定失效的层及其下游；不得删除其他项目缓存、仍有效的上游层、`work/<项目目录名>-project-onboarding/`、历史任务目录、历史用例或输出文件。

## 3. 候选证据文件与项目指纹

### 3.1 候选证据

项目全局文件清单至少覆盖：

- 项目 `需求来源策略.json`、项目说明和项目级规则。
- 已确认的新项目接入记录，或者旧项目兼容依据；接入草稿只用于阻断和确认，不作为业务规则证据，历史缓存中的业务结论也不得因兼容接入而复用。
- 全部 `context/` 需求、角色权限、业务对象、页面架构和沟通记录。
- 原型入口、原型说明、页面、公共批注、公共 Mock、共享配置、共享组件和页面脚本。
- 项目内存在的接口契约、服务端或前端代码、数据库约束和自动化测试。

项目 `需求来源策略.json` 中的 `派生需求清单` 仅表示允许自动同步修改的文件，不是候选证据白名单。配置中的 `公共证据清单` 应直接纳入；未配置该字段时，仍需发现并纳入全部现存 `context/` 文件、项目说明引用文件以及扫描中识别出的公共或关联来源。未被 Git 跟踪的现存项目文件也要建档，不能因其未出现在派生需求清单或版本索引中而忽略。

已有测试用例、历史 Excel、历史任务 JSON、历史扫描结果和历史缓存单独登记为 `历史参照候选`，不进入当前业务证据集合，也不能证明业务规则。它们可以提供检索词、历史覆盖范围和关联线索；任何线索必须回到当前需求、原型、接口、代码或用户确认中复核后才能进入证据索引。截图、图片、字体、纯样式资源、生成物和任务临时文件可以只建档不解析；必须按文件或稳定目录规则记录排除原因。任何被当前需求、页面、批注、Mock、配置或代码直接引用的文件不能仅以扩展名为由排除。

### 3.2 文件记录

每个候选证据文件记录：

```text
相对路径, 文件大小, 修改时间, SHA-256, 文件类别, 输入角色候选
```

项目指纹由按相对路径排序后的候选证据文件记录、项目目录名、接入记录或旧项目兼容依据中的稳定项目标识和扫描 Schema 版本共同计算。分支和提交只作为扫描基线，不作为首次接入身份变化的单独判据。不能只依赖修改时间判断文件是否变化。

## 4. 扫描模式选择

扫描模式只能是：

- `full`：首次扫描或没有可验证缓存，完整建立证据索引和依赖关系。
- `incremental`：缓存有效，仅重新读取变化文件及其受影响依赖。
- `fallback-full`：原计划增量扫描，但发现缓存失效、未知依赖或映射无法闭合，自动改为全量扫描。

### 4.1 证据层必须使用 full 的条件

满足任一条件时使用 `full`：

- 没有项目级缓存，或者缓存 JSON 无法解析、缺少必填字段、状态不是通过。
- 用户明确说明项目已整体替换，或要求强制全量扫描。
- 新项目首次接入刚完成，或者接入记录中的稳定项目标识、正式入口或来源策略发生变化。
- 项目目录名、来源策略或扫描 Schema 版本发生变化。
- 证据原子提取 Schema 或依赖索引 Schema 发生不兼容变化；普通业务规则、生成规则或工作簿规则变化只使声明的最早受影响层及下游失效。
- 新增、修改、删除的候选证据文件合计达到 30 个。
- 变化文件数除以前后候选证据文件数较大值达到或超过 20%。

### 4.2 可以使用 incremental 的条件

只有同时满足以下条件才能使用 `incremental`：

- 上一次缓存状态为通过，项目标识、证据输入哈希和准备复用层的 Schema 一致；规则基线变化已声明最早受影响层并废弃对应下游。
- 变化数量未触发全量阈值。
- 每个变化文件都可以在依赖映射中定位所属端、模块、业务对象和下游影响。
- 未变化证据的当前 SHA-256 与缓存一致。

### 4.3 切换为 fallback-full 的条件

增量扫描中出现以下任一情况，立即停止复用并切换为 `fallback-full`：

- 变化文件无法分类或无法定位业务对象。
- 依赖目标文件已删除且没有明确替代关系。
- 新关联指向缓存中未建档的端、模块、公共配置或第三方来源。
- 依赖映射断裂，不能形成上游来源、当前行为和下游结果的闭合链路。
- 读取过程中发现缓存记录与实际文件内容不一致。

### 4.4 失效层清理门禁

项目接入、正式证据入口和来源策略前置门禁通过，且扫描模式和最早失效层确定后，必须在语义读取开始或继续之前执行以下步骤：

1. 将缓存目标解析为当前项目唯一的 `work/<项目目录名>-global-evidence-cache/`，核对目录名与当前项目稳定标识；禁止使用未解析变量、通配符、工作区根目录或其他项目目录作为删除目标。
2. 读取旧缓存仅限于模式判断和清理审计；按层列出待失效文件，记录层名、相对路径、SHA-256 和文件数量，不得把已失效层的业务结论带入本次结果。
3. 在本次任务的 `global-evidence-scan-result.json` 先建立 `缓存清理` 记录，再删除或隔离失效层及其下游。目录不存在或没有待失效文件时也要记录成功，清理数量为 0。
4. 清理后重新枚举目标层；存在被判定失效的旧文件、文件无法读取或清理失败时，将状态标记为 `失败` 并阻断扫描。仍有效上游层必须保留并记录复用依据。
5. 全部交付门禁通过后，才能原子发布新的层产物并更新 `latest.json`。扫描中途失败时不得发布本次层结果，也不得恢复或继续使用已判定失效的层。

`full` 和 `fallback-full` 从 `evidence-atoms` 层开始失效；一旦触发，立即停止增量语义读取，执行上述清理门禁，再从当前证据建立完整证据原子和下游索引。只做文件清单与哈希的 `inventory` 层若输入完全一致可以保留，但必须在任务快照记录。

## 5. 全量扫描流程

1. 建立候选证据文件清单和项目指纹。
2. 按第 4.4 节记录并清理证据原子及全部下游失效层；清理校验未通过时停止。
3. 读取目标模块全部直接来源、公共需求、公共批注、公共 Mock、共享配置和共享组件。
4. 从项目入口、需求、批注、Mock 字段和配置识别其他端或模块依赖；历史用例只能提出待复核的依赖线索，不能直接建立依赖或业务规则。
5. 按依赖继续读取管理后台、公会端、第三方和下游记录来源，直至关联闭合。
6. 建立“文件 -> 页面或章节 -> 端 -> 模块 -> 共同业务对象 -> 角色或身份 -> 动作 -> 稳定规则标识 -> 正式用例/需求待确认”映射。
7. 对全部拟判定的规则缺失按第 7 节执行复核，撤销已有来源明确证明的错误缺口。
8. 对未纳入语义读取的文件记录类别和排除原因。
9. 保存任务快照；任务通过交付门禁后再创建新的项目级缓存。

全量扫描要求全量建档和完整读取相关证据，不要求逐行解析与当前模块无关且已经记录排除原因的文件。

## 6. 增量扫描流程

1. 重建轻量候选证据清单并与上次项目指纹比较。
2. 分类新增、修改、删除和疑似重命名文件；删除与新增文件 SHA-256 相同时可以标记为重命名候选，但仍需确认业务位置变化是否影响依赖。
3. 读取全部变化文件。
4. 根据依赖映射向上检查规则来源，向下展开所有受影响模块和观察端。
5. 目标模块直接来源即使未变化，也必须通过当前 SHA-256 验证后才能复用证据结论。
6. 公共需求、公共批注、公共 Mock 或共享配置变化时，重新读取其全部下游依赖，不只读取当前页面。
7. 更新关联映射、证据原子、归一化规则、覆盖清单和受影响已有用例；历史用例变化只触发历史比较层，不得覆盖当前证据结论。
8. 对新增、变化或受影响的拟缺失规则按第 7 节重新执行复核；缓存中的旧缺口不得在来源变化后直接复用。
9. 保存本次任务快照；交付通过后以新结果原子替换项目级缓存。

## 7. 规则缺失判定复核

任何规则进入 `证据缺口` 或“需求待确认”前，执行以下步骤：

1. 将拟判定缺失的内容拆为业务对象、角色、动作、前置状态、目标状态、限制条件和可观察结果。
2. 为每个检索对象补充原文简称、同义词、旧称、页面名称和字段名。例如“连麦”还应结合“邀请”“接受”“拒绝”“连线”“PK 面板”和对应页面名称检索。
3. 在全部已登记及扫描发现的关联来源中检索；不能只检查 `派生需求清单`、目标端需求或单个页面。
4. 对每个命中阅读所属章节、表格整行、相邻条件和直接引用，记录其能够证明的规则。仅有标题命中或搜索摘要不算完成语义读取。
5. 合并同一规则的多来源命中，记录适用角色、端、房型、状态或其他范围；一个来源明确、另一个来源未提及，不记为冲突。
6. 命中内容足以形成确定结果时，写入证据索引和覆盖清单，不得继续标记为缺失。命中相互冲突且不能消解时记录来源冲突；全部相关来源均完成复核仍无确定结果时，才记录证据缺口。
7. 项目说明引用文件缺失、应读来源无法读取、关联链路未展开或复核记录不完整时写入阻塞项，不得以“需求待确认”代替扫描阻塞。

每项复核至少记录：

```text
规则标识, 业务对象, 角色, 动作或状态, 检索词, 已查文件, 命中位置, 命中规则, 采用结论, 未采用原因, 复核状态
```

复核状态只能是 `已确认规则`、`来源冲突`、`证据缺口` 或 `阻塞`。

## 8. 原型同步衔接

全局扫描先完成项目指纹比较、模式选择和关联范围计算，再执行 `prototype-primary` 项目的原型与需求清单同步。

已配置 MainBasis 的项目按 `AGENTS.md` 的 `BASIS-01` 和同步指令第 3.9 节衔接：本扫描属于上游需求更新阶段。MainBasis 两文档登记为汇总输出，不参与上游规则自证；扫描和 context 同步完成后更新两文档并固定需求版本，再进入只使用两文档的用例阶段。上游新增、删除或内容变化使需求版本需要重新核对，不能因为 MainBasis 文件没变化就沿用旧用例输入。

- `full` 和 `fallback-full`：按本次完整关联范围固定原型基线并同步。
- `incremental`：至少同步发生变化的原型、其公共依赖、受影响页面和对应 `context/` 章节。
- 同步修改了 `context/` 时，将修改后的文件重新计算 SHA-256，更新本次证据基线后再继续生成。

## 9. 双重基线校验

任务开始读取或复用证据时保存第一次基线。生成最终 JSON 和 Excel 前，对全部已读取或复用证据再次计算 SHA-256。

- 两次一致：允许继续交付。
- 任一文件变化：本次扫描和生成结果失效，不能只重导出 Excel；必须重新比较项目指纹、选择扫描模式并更新受影响用例。
- 文件在第二次校验时缺失或新增关联来源：按依赖失效处理，必要时切换 `fallback-full`。

## 11. 状态与阻断

扫描状态只允许：

- `通过`：扫描和关联闭合，无阻塞项。
- `有非阻塞待确认`：扫描完整，但业务规则本身缺失或冲突，已进入“需求待确认”。
- `阻塞`：扫描、缓存、基线或关联存在无法限定影响范围的系统性不完整，禁止生成当前批次的最终 JSON 和 Excel。

以下情况无法限定到具体规则或模块时必须阻断：新项目接入未确认且不符合旧项目兼容依据、接入记录或兼容依据与稳定项目标识不一致、项目指纹缺失、扫描模式或最早失效层无依据、首次接入或首次兼容扫描未执行 `full`、失效层未在语义读取前成功清理或缺少记录、关键变化仍复用已失效证据、采用证据哈希不一致、目标或公共来源未读取、已发现依赖未展开、排除原因缺失、关联映射无法闭合、拟判定缺失的规则没有完成 `规则缺失复核`、项目说明引用文件缺失且没有明确替代关系、历史用例或历史缓存被写入当前业务证据集合、输出前复核未通过。能够定位到具体规则、角色或模块且其余证据闭环完整时，按 `AGENTS.md` 的 `GATE-01` 隔离受影响内容并继续处理。
